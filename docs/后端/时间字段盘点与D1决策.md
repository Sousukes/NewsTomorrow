# 时间字段盘点与 D1 决策依据

> 本文是 backlog **D1**（`String(30)` → `TIMESTAMP`）的决策材料，
> 由 P1-50 产出。**本批不改 schema**，只把"改之前必须知道的事"查清楚并钉住。
> 结论摘要在最后一节，先看结论也行。

## 一、现状盘点

### 1.1 列的类型与口径

`app/models.py` 里共 **36 个 `String(30)` 列**，其中：

| 类别 | 列 | 口径 |
| --- | --- | --- |
| 绝对时间戳（UTC aware ISO，A3 后统一） | `created_at`（多表）、`updated_at`、`reviewed_at`、`hidden_at`、`deleted_at`、`viewed_at`、`name_reviewed_at`、`last_fetched_at`、`last_alerted_at`、`next_retry_at`、`hot_score_at`、`published_at`、`at`（健康事件） | `now_str()` 写入，秒精度带 `+00:00` |
| **展示文案**（不是时间） | `news.time`、`comments.time`、`messages.time` | 「1小时前」「刚刚」等，**不可排序、不可比较** |
| 业务 ID（`String(30)` 但不是时间） | `channel`、`key`、`source_key` 等 | 与时间无关，不在 D1 范围内 |

**好消息**：`String(30)` 列的 `default=` **全部**是 `now_str`，没有混入其他默认值；
所有"名字像时间"的列也都是 `String(30)`（没有漏网的 `DateTime`）。

### 1.2 比较发生在哪里（这才是 D1 的真正风险面）

| 位置 | 写法 | 改列类型后 |
| --- | --- | --- |
| `feeds/health.py` | **SQL 侧** `RssSourceHealthEvent.at >= cutoff`，cutoff 是 ISO **字符串** | PG 的 `timestamptz` 与字符串比较会隐式转换；**SQLite 没有原生时间类型**，仍是字符串——双端行为必须一致 |
| `ranking.py` / `scheduler.py` | Python 侧算 cutoff、写 `hot_score_at` | 与列类型无关，`parse_dt`/`now_str` 是统一入口 |
| `feeds/alert.py` | Python 侧 `_parse(row.last_fetched_at)` 与 aware datetime 比较 | 不受影响 |
| 排序 | `coalesce(published_at, '')`、`coalesce(created_at, '')` DESC | **关键**：`''` 与 `NULL` 语义不同。改类型后 `coalesce(x, '')` 会报类型错，必须同时改成 `NULLS LAST` 或保留一个哨兵 |

## 二、本批发现并修掉的两个真问题

### 2.1 用户可见 bug：新建评论显示原始 ISO 串

`comments.time` / `messages.time` 两列同时装着两种东西：

- 用户新建路径：`time=ts, created_at=ts`，`ts` 是 **ISO 时间串**（`routers/comments.py`）；
- 演示种子：`time="1小时前"` 之类的**展示文案**（`seed.py`）。

`to_out` 原样透传，于是**用户刚发的评论显示 `2026-10-18T14:42:17+00:00`**。

修法不是"换一种存法"（那要迁数据），而是**展示文案由绝对时间推导**：
新增 `models.display_time(stored, absolute)`，输出侧统一调用。规则：

- 能解析成 ISO 的 → 现算相对文案（`刚刚` / `N 分钟前` / `N 小时前` / `N 天前`，超过一周给日期）；
- 已经是展示文案（解析不了）→ **原样返回**，不覆盖演示数据；
- 都没有 → 回落到另一列，仍为空则返回空串。

**这同时消掉了 D1 的一个障碍**：展示型列不再需要"两种格式共存"，
改类型时可以直接把这三列排除在迁移范围外（它们根本不是时间）。

### 2.2 `time` 列的默认值是个陷阱

`comments.time` / `messages.time` 的默认值是 `now_str`，与列的实际语义
（展示文案）矛盾——只要哪条新建路径忘了传 `time`，就会写进一个 ISO 串。
本批通过输出侧推导让默认值不再影响显示，但**默认值本身建议后续改成 `""`**
（与 `news.time` 一致），避免"看着是时间其实是文案"的误用。这一步留给 D1 一起做。

## 三、D1 的前置条件（现在已满足的部分）

D1 要把绝对时间列改成 `TIMESTAMP`。它成立的前提是「同格式 ISO 的字典序 = 时间序」
——A3 统一了写入口径，0027 迁移回填了存量偏移，**但这条契约此前没有任何断言守着**。

本批新增 `tests/test_time_contract.py`（14 项），把契约钉住：

- `now_str()` 输出必须是 `YYYY-MM-DDTHH:MM:SS+00:00`（正则 + `parse_dt` 复核）；
- 字典序 == 时间序（这是迁移回填"只补偏移不改数字"能保序的依据）；
- `models.py` 里**不得**再出现 naive `datetime.now()`——用 **AST** 扫调用节点，
  不用子串匹配（文档字符串里那句"不要再引入 datetime.now()"会把护栏自己绊倒）。

## 四、执行 D1 时必须同时处理的清单

1. **`coalesce(x, '')` 会因类型变化报错**：`published_at` / `created_at` 的排序
   依赖它把 NULL 兜成空串沉底。改类型时同步改成 `NULLS LAST`（PG 原生），
   SQLite 侧确认等价写法。
2. **SQLite 无原生时间类型**：`DATABASE_URL` 允许 SQLite 兜底，
   `alembic check` 也只在 PG 上跑（SQLite 反射不了 FK/GIN）。迁移脚本必须
   **分方言**，且 downgrade 要空操作（多数类型转换不可逆）。
3. **健康事件的 `at >= cutoff` 是 SQL 侧字符串比较**：改类型后 cutoff 应由
   Python 传 `datetime` 对象（`sa_bindparam`），而不是继续拼字符串。
4. **展示型三列（`news/comments/messages.time`）不进迁移**：它们不是时间。
5. **回填口径与 0027 一致**：只补偏移、不改数字，保证顺序精确保留。

## 五、实测实验结果（P1-51，`tests/test_time_migration_spike.py`）

> 本节是**跑出来的**，不是推演的。实验用 SQLite（本地无 PG 守护进程），
> 而 SQLite 恰是 ALTER 更难的一端：没有原生时间类型，改列要整表重建。
> 4 项断言永久留在 CI 里，作为 D1 的前置约束。

### 实验结论一：存量列里混着五种东西

| 实际值 | 来源 |
| --- | --- |
| `2026-10-18T14:00:00+00:00` | A3 之后的写入 |
| `2026-10-18T14:00:00`（naive） | 0027 回填之前的存量 |
| `''`（空串） | 代码里 `published_at != ""` 的哨兵值 |
| `NULL` | 「没有时间」的正确表达 |
| `刚刚` | 展示文案误入时间列 |

### 实验结论二（决定性）：**空串与展示文案会让迁移直接失败**

`batch_alter_table` 在重建表时要把每行按新类型解析，遇到 `''` 与 `刚刚`
直接抛错——**不是"变成 NULL"，是整表迁移失败**。

这意味着：**任何 D1 方案都必须先做数据清洗**，而且清洗与列类型无关，
它是独立的前置步骤。原计划里没有这一步，是方案里的真实缺口。

### 实验结论三：干净数据上，转换后排序仍等价于时间序

把两行合法 ISO 值转成 `DateTime(timezone=True)` 后，`ORDER BY at DESC`
的次序与时间序一致；`NULL` 原样保留（不会被填成"零时间"）。

## 六、D1-a 的判断：**不成立，不做**

按上一版的划分，D1-a 是"只排序、不参与 SQL 范围过滤"的低风险列。逐列核实后：

- `news.published_at` → 抓取保留期清理 `published_at < cutoff`（`ingest.py`）
- `comments.created_at` → 管理端 **keyset 游标**比较（`admin/comments.py`）
- `news.hot_score_at` → 热度衰减筛选 `< cutoff`（`ranking.py`）
- `hit_logs.*.created_at` → 命中日志保留期清理（`hit_logs.py`）

**这四类都是 SQL 侧比较，没有一个是"只排序"。** 剩下真正只写入的列
（`hidden_at` / `deleted_at` / `reviewed_at` / `last_fetched_at` …，共 11 处写入点）
收益只有"类型诚实"，代价却是：11 处写入点改造 + 引入**第二套写入口径**
（`now_dt()` 与 `now_str()` 并存——正是 A3 刚消除的那类漂移）
+ 一次不可逆的双方言迁移。

**结论：把低风险列单独拿出来做，收益不足以抵消它引入的新漂移面。**

## 七·补（P1-55）：最终定案——「只排序/只写入」列不迁

P1-53/54 迁完了唯一**纯范围过滤**列（`rss_source_health_events.at`），并造好
重建工具与演练。按约定下一步是迁「只排序/只写入」列。动手前逐列核对了
SQL 用法与写入路径，结论是：**这些列不该迁**。

### 逐列核实结果

| 列 | 实际用法 | 结论 |
| --- | --- | --- |
| `user_history.viewed_at` / `user_favorites.created_at` | 排序键，但写入走 `_merge`——`func.max(time_col)` + `_parse_iso` + `.isoformat()` 的时间算术 | 迁类型要连带改 `_merge_base` 的参数类型 |
| `comment_likes.created_at` / `message_reads.created_at` | 只写入 | 纯写入，收益仅类型诚实 |
| `comments.hidden_at/deleted_at/reviewed_at`、`news.hidden_at`、`users.name_reviewed_at` | 只写入，**但有输出点**（`hiddenAt`/`reviewedAt`） | 迁类型要逐个过 `iso_utc` |
| `rss_sources.last_fetched_at/next_retry_at` | `alert.py` 里 Python 侧 `_parse` 比较；有输出点 | 同上 |
| `search_logs.created_at` | `>= cutoff` / `< cutoff` **范围过滤** | 属 D1-2 |
| `messages.created_at` | `coalesce(created_at,'')` 排序键 | 改类型要换 `NULLS LAST` |

**结论：根本没有「纯」的低价值列。** 即便「只写入」的列，要么写入路径纠缠着
`_merge` 的时间算术，要么有输出点要逐个改。为「类型诚实」付出这些验证面，
不划算——P1-53 已经用一次静默毁数据证明，这类迁移的真实风险远超纸面收益。

### D1 的最终范围

1. **已迁**：`rss_source_health_events.at`（唯一纯范围过滤列，0030）——
   这是 D1 里唯一「现在就有功能价值」的列（窗口查询用上了真实类型 + 参数绑定）。
2. **不迁**：所有「只排序/只写入」列（上表全部）——收益仅类型诚实。
3. **按需再迁（D1-2）**：`news.published_at`、`news.hot_score_at`、
   `hit_logs.*.created_at`、`search_logs.created_at`、`comments.created_at`
   ——这些才是「解锁数据库时间函数」的地方，但**当前不需要**（A3 之后的
   字符串 ISO 比较已经正确）。等到真正要用数据库时间函数（比如保留期清理
   想下推给数据库、或做时间窗口聚合）时，再逐列迁，那时工具与演练都已就位。

## 七、修正后的建议顺序

1. **D1-0（先做，与列类型无关）**：数据清洗——
   把 `''` 哨兵归一为 `NULL`、清理误入时间列的展示文案；
   这一步本身就消掉了 `coalesce(x, '')` 的必要性（可直接换 `NULLS LAST`），
   且**顺带修掉一个既有的正确性隐患**（空串参与排序/过滤的语义歧义）。
2. **D1-1（再做）**：把参与 SQL 侧比较的列改 `TIMESTAMP`，
   cutoff 一律改**参数绑定**（传 `datetime` 对象，不拼字符串），
   SQLite 侧确认等价写法；downgrade 空操作并在提交信息里写明不可逆。
3. **展示型三列（`news/comments/messages.time`）不进任何一批**——它们不是时间。

第 1 步是真正该先做的：它不依赖任何设计决策，做完之后 D1-1 的风险面明显变小。
