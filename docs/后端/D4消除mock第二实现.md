# D4 消除 mock 第二实现 · 方案评估（已实施）

> 状态：**已实施**（P1-83 差分契约测试）。方向 B 落地，A / C 按评估否掉。

## 一、现状核实

### 1.1 「第二实现」的实际规模

| 位置 | 规模 | 内容 |
| --- | --- | --- |
| `mingri-toutiao-vue/mock-server/server.mjs` | **378 行 / 约 99 个路由** | 用 Node 手写的第二套后端 |
| `src/api/news.ts` | 29 处 mock 相关 | `USE_MOCK` 分支里**又一份**列表/排序/搜索/关注流的 JS 实现 |
| `src/api/*.ts`（follows / comments / me …） | 同款内联分支 | 每个模块各有一份 |
| `src/data/mockNews.ts` / `mockComments.ts` | 87 行 + | 种子数据 |

也就是说：一个接口契约最多有**三份**实现——FastAPI、`mock-server`、前端内联分支。

### 1.2 已有的护栏（这是关键，容易被忽略）

`scripts/contract-check.mjs` 已经能做**前后端契约校验**：它复刻前端的解包/鉴权/
归一化逻辑，对后端跑一遍，校验字段名、错误码、鉴权头。而且**注释明确写着
「对 FastAPI 后端（或本地 mock 后端）跑一遍」**——它已经可以同时打两边。

**所以 D4 的真正缺口不是「有两份实现」，而是「两份实现之间没有人比对」。**
契约漂移的表现是：mock 演示好好的，接真后端某一处字段对不上——而这种漂移
**当前不会被任何自动化发现**，因为契约脚本只验「前端期望 vs 被选中的那一端」。

### 1.3 另一条已存在的诚实边界

mock **刻意不模拟**需要 3 个不同账号才能触达的行为（举报阈值自动处置的
`autoHidden` 恒 false）。这不是缺陷，是明确记录在案的取舍——
评估方案时不能把它当成"待消除的漂移"。

## 二、三个选项

### A. 全部删掉：mock-server + 内联分支

- 收益：只有一份实现，契约漂移从根上消失。
- 代价：**丢掉「不起后端就能跑」的能力**。`USE_MOCK` 的存在意义就是这个，
  演示、Storybook、单测都依赖它；删了之后新人 clone 下来必须先起 FastAPI + PG。
- 判定：**不建议**。用一个确定的问题换一个不确定的收益。

### B. 保留两份，加**差分契约测试**（推荐）

把 `contract-check.mjs` 的一次运行拆成「打 mock」与「打真后端」两次，
对同一组请求比对**响应形状**（字段集合、类型、错误码），不一致即失败。

- 收益：漂移在 CI 暴露，且**是具体到字段的报错**（`mock 的 /news 缺 sourceKey`）；
- 代价：约 150~250 行 Node 脚本 + 需要一条"同时起 mock 与真后端"的 CI 步骤；
  比对要容忍合理差异（值不同但形状同：id、时间、条数）。
- 保留离线演示、保留 Storybook / 单测的 mock 依赖。

### C. 从 OpenAPI 生成 mock-server

FastAPI 自带 `/openapi.json`，可以生成路由骨架。

- 收益：mock 与真后端共享同一份 schema，结构上不可能漂移。
- 代价：mock 的价值一半在「**刻意不真实**」的语义（阈值不模拟、种子数据的
  特定形状、`autoHidden` 恒 false）——生成出来的 mock 会把它们一起模拟掉，
  于是要么给生成器开一堆例外，要么丢掉这些诚实边界。
- 判定：**不建议**。它与 1.3 的既有取舍冲突。

## 三、5 个决策点（待确认）

### D1 方向：B（差分契约测试）？

**推荐 B**。它修的是真问题（两份实现之间无人比对），且不动现有能力。
A 用确定的问题换不确定的收益；C 与「mock 刻意不真实」的既有取舍冲突。

### D2 比对粒度：字段形状还是逐值相等？

**推荐字段形状 + 关键枚举值**。逐值相等不可能成立（id、时间、条数都不同），
要比的是：**字段集合、字段类型、错误码集合、必填项**。

### D3 是否给真后端也跑一遍 diff（需要同时起两个服务）？

**推荐是**，但放进**单独的 CI 步骤**（不是每次跑），避免把本地开发链路绑死在
"必须同时起两个服务"上。可用环境变量控制是否启用。

### D4 mock 的「刻意不真实」清单要不要显式化？

**推荐显式化**：在 `mock-server` 顶部用一份清单写清「哪些行为刻意不模拟」
（当前只有举报阈值一条，但清单化之后新增 mock 端点时必须表态）。
这比散落的注释更防回归。

### D5 内联分支（`api/*.ts` 的 `USE_MOCK`）要不要一起收？

**推荐先不收**。它们与 mock-server 是**两套不同用途**：内联分支服务"某个模块
单独跑单测/Storybook"，mock-server 服务"整站演示"。两者用同一份种子数据即可，
不一定需要同一份代码。可以先做 B，观察 diff 测试是否暴露内联分支的问题。

## 四、拆批建议（若 D1~D5 按推荐）

**P1-83 差分契约测试**：
1. 把 `contract-check.mjs` 重构成「请求清单 + 断言」结构，可指定目标 BASE；
2. 新增 `contract-diff.mjs`：同一清单打 mock 与真后端，比对字段形状与错误码；
3. `mock-server` 顶部加「刻意不模拟」清单；
4. 接进 CI（独立步骤，环境变量控制）；
5. 契约测试命名沿用现有契约测试风格（H 编号）。

**规模**：主脚本重构 + 1 个新脚本 + mock-server 注释清单，预计 5~8 项测试。

**预期效果**：以后任何一批改了后端契约而没同步 mock，CI 会给出
`mock /news 缺 sourceKey` 这类**具体到字段**的报错——而不是等演示时对不上。
