# E4 多源转载去重 · 设计方案（含对 backlog 原文的证伪）

> 状态：**方案已定（证伪 + 收敛范围）**。本轮在真实 PG 库（491 条可见资讯）上做了
> 两轮数据探测，**结论与 backlog 原文的说法不一致**，故先把结论写下来再谈实现。
> 来源：backlog E4「同源稿件多源入库会重复出现；已有 `similarity` 可做标题聚类」。

## 一、先量：backlog 的前提**部分不成立**

### 1.1 源分布（可见资讯 491 条）

| 来源 | 条数 |
| --- | --- |
| 中新网·体育 | 124 |
| AIHOT·精选 | 82 |
| 新华社 / 新华财经 / 军事频道 / 人民日报 / 财经周刊 / 中国天气 | 各 1（种子数据） |

真正跑 RSS 的是**两个源**，且主题域不同（体育 vs 精选）。跨源重复的存在空间本就有限。

### 1.2 跨源重复：存在，但**相似度很低**

| 相似度阈值 | 跨源配对数 |
| --- | --- |
| ≥ 0.95 | 0 |
| ≥ 0.9 | 0 |
| ≥ 0.8 | 0 |
| ≥ 0.7 | 0 |
| **≥ 0.6** | **0** |
| ≥ 0.5 | 1 |

真实存在的跨源重复长这样（**同一事件、标题被改写**）：

| sim | A | B |
| --- | --- | --- |
| 0.500 | [中新网·体育] 郑钦文首进中网女单决赛 将与米拉·安德列娃争冠 | [中新网·要闻] 郑钦文首进中网女单决赛 |
| 0.425 | [中新网·财经] 今年前三季度全国铁路发送旅客37.1亿人次 创历史同期新高 | [中新网·要闻] 前三季度中国铁路发送旅客超37亿人次 创历史同期新高 |
| 0.300 | [中新网·体育] 2小时03分10秒！2026北京马拉松诞生新的赛会纪录 | [中新网·要闻] 2026北京马拉松开跑 |

### 1.3 反例：高相似 ≠ 同一条（**这条最要命**）

同源的两条：

| sim | A | B |
| --- | --- | --- |
| **0.652** | CBA季前赛汕头站：广州队不敌**天津队** | CBA季前赛汕头站：广州队不敌**山东队** |

这是**两场不同的比赛**。按相似度合并 = **丢内容**，而且用户完全不会察觉——
他只会觉得"怎么少了一条"，比多一条更难解释。

### 1.4 真实的重复其实是**同源重复入库**

完全同标题的组共 3 组（6 条），**全部同源**：

| 标题 | 来源 | 两条的发布时间 |
| --- | --- | --- |
| 2025年欧盟进口纯电动汽车逾四成来自中国 | 中新网·要闻 | 14:12:58 / 15:11:05 |
| 宁夏枸杞鲜果首次经银川关区冷链直供香港 | 中新网·财经 | 12:56:44 / 13:39:30 |
| 赵乐际同越南国会主席陈青敏会谈… | 中新网·要闻 | 13:55:14 / 14:22:24 |

`id = sha1(url || title)`（`feeds/fetcher.py::_stable_id`），两条 id 不同说明
**同一篇稿件在两个抓取周期里 URL 变了**（源改了链接 / 加了跟踪参数），于是
`upsert_news` 的按 id 判重失效，插入了第二条。

另有 4 对同源标题微调的重复（sim 0.65~0.80），如同「…专题音乐会在京举行 /
在北京举行」、「证监会召开… / 中国证监会召开…」——源自己改了标题重发。

## 二、结论：标题相似度**做不了**「该不该合并」的判据

把上面三条放在一起看：

- 想抓到跨源改写型重复，阈值得降到 **0.3 左右**；
- 但 0.3 会把大量**同主题的不同稿件**卷进来（1.3 的反例在 0.652 就已经误判了）；
- 阈值留在 0.6+ 则**一条跨源重复都抓不到**（1.2 的表里 ≥0.6 是 0 对）。

即：**低阈值误合并（丢内容），高阈值没效果**。中文新闻标题改写后相似度天然
只有 0.3~0.5，而不同稿件之间又能轻易达到 0.65——两个分布是**重叠的**，
不存在能把它们分开的阈值。

这与 P1-51 证伪 D1-a 是同一类结论：**不是"还没调好参数"，是信号本身不够。**

## 三、决策点（3 个）

### D1 跨源合并做不做？

**推荐：不做列表合并。** 三条理由：

1. 信号不可靠（§二），误合并的代价是**静默丢内容**；
2. 跨源重复在**当前源配置下稀少**（≥0.6 为 0 对），收益极小；
3. "同一事件的其它报道"这个功能**已有 `/api/news/{id}/related` 在做**
   （P1-4 的相关推荐，同样基于标题相似度）。再做一个是重复建设。

### D2 同源重复入库要不要修？

**推荐：修。** 这是**确定性缺陷**——同一篇稿件因为 URL 变化被插了两条，
用户会看到两条一模一样的新闻。判据可以收紧到不会误判的程度（见 D3）。

### D3 阈值怎么定？

**推荐：同源 + 标题相似度 ≥ 0.9，或标题完全相同（去空白后）。**
- 同源是前提（跨源改写不动）；
- 0.9 远高于 1.3 反例的 0.652，同源同标题组都是 1.000，标题微调的几组在
  0.65~0.80——**0.9 恰好把它们分开**，只吃掉"确实是同一篇"的那部分。

> 附带效果：源改标题重发（sim 0.65~0.80）**不会被吃掉**。这是刻意的——
> 那是源的行为，我们不该替它决定"这两条是一条"，留着由运营判断更安全。

## 四、方案（E4-a：入库前同源近邻判重）

在 `feeds/ingest.py::upsert_news` 的新增分支里加一道判重：

1. 对每条**待新增**的 item，在同一个源内查"标题近邻"
   （`source_key` 相同 + `similarity(title, :title) >= 0.9`，PG 路径；
   SQLite / 无 trgm 时**退化为标题完全相等**，与 `_search_fallback` 同一处方）；
2. 命中则**更新那条**（按现有增量更新语义：刷新标题/摘要/正文/图片/时间），
   不新增行；
3. 不命中才 `db.add`。

三条边界：

- **只在新增分支判重**：已存在的行按 id 命中，走的是更新路径，不受影响；
- **批量内自判重**：同一批 items 里若两条互为近邻，第二条也不能新增
  （否则同一批里照样插两条）；
- **不做历史数据的回溯合并**：现有 3 组重复保留，由下一节的清理脚本处理。
  理由是把"以后不再产生"和"改历史"分成两件事——后者风险高得多，且重复
  本身不影响功能。

## 五、刻意不做

- **跨源合并**（D1，已证伪）；
- **按正文/内容指纹去重**：P1-70 已量出 `content` 普遍只有 12~85 字，
  信号比标题还弱；
- **自动删除历史重复**：改为提供一次性清理脚本（人工确认后执行），
  不在自动链路里删数据。

## 六、拆批建议

1. **P1-74**：`upsert_news` 同源近邻判重（含批量内自判重）+ 测试
   （真近邻合并 / 反例不合并 / SQLite 退化 / 批量内两条）；
   另提供 `scripts/prune_duplicate_news.py`（**默认只报告，加 `--apply` 才删**）。
2. 跨源去重：**关闭**，按 D1-a 的先例记入 backlog（"已证伪，不做"）。
