# D7 领域事件 outbox · 方案评估（结论：**不建议做 outbox**）

> 状态：**待确认**。本批只做核实与结论，未改代码。
> 结论先说：backlog 原文「改事件表 + 异步消费」在这个代码库里是**过度设计**——
> 所有"旁路动作"都落在**同一个数据库**内，不存在 outbox 要解决的"跨系统可靠投递"。
> 真正该修的是**三处半途而废的写入**与**失败不可观测**。

## 一、现状核实（逐条读代码确认）

### 1.1 已经是「同事务」的（不需要改，且是好范例）

| 动作 | 证据 | 说明 |
| --- | --- | --- |
| 审计日志 | `routers/admin/_shared.py::record_audit` **不 commit**，由调用方随业务一起提交 | 注释里写得很清楚：「改成功了但没留痕比改失败更糟」 |
| 评论 + 冗余计数 | `routers/comments.py` 中 `db.add(c)` 与 `news.comment_count += 1` 同一次 `commit()` | — |
| 举报写入 | `app/reports.py` 单次 `db.commit()` | — |
| 收藏/历史/关注/负反馈 | 均单表单次提交 | — |

**这一条直接削弱了 D7 的前提**：如果连审计都能同事务，说明"旁路必须异步"在本项目并不成立。

### 1.2 真正半途而废的（三处，全部是"两次 commit"）

| 位置 | 现状 | 失败后果 |
| --- | --- | --- |
| `comments.py::create_comment` | ① 评论 + 计数 commit ② `notify_*` 再 commit，包在 `try/except` 里，失败只 `logger.warning` | 评论成功但**通知永久丢失**，用户侧无任何痕迹 |
| `comments.py::set_like` | 同上（点赞通知） | 同上 |
| `app/reports.py::submit_report` | ① 写举报 commit ② 达阈值才 `_auto_hide` 再 commit | 举报成功但**自动处置没生效**；且阈值检查只在"提交新举报"时触发，**不会自愈**（要等第 N+1 个人举报） |

### 1.3 派生数据（不需要事务保证）

| 动作 | 现状 | 判断 |
| --- | --- | --- |
| `bump_hot_score` | 评论/点赞后调用，失败不影响主流程 | 热度可由 `recompute_hot_scores` 重算，**不需要 outbox**；但需要"重算确实会跑到"（已有定时任务） |

### 1.4 结论：outbox 的经典前提在这里不成立

outbox 模式解决的是「**本地事务 + 外部投递**」的一致性（发邮件、推送、投递到消息队列）。
本项目的"旁路"全部是同库写入——**同库写入可以直接放进同一个事务**，
这正是审计日志已经采用的做法。为同库写入引入 outbox，代价是：

- 多一张表 + 一个消费者 + 至少一次投递语义 + 幂等键；
- 从"同步可见"变成"最终一致"（评论后通知列表要等消费者跑一轮）；
- 出错时的排查路径变长（事件是否入表？消费者是否跑到？是否重复消费？）。

换来的收益只是"通知写入失败不会拖垮评论"——而这个失败概率与评论插入同级
（同一个 DB、同一类操作），真到 DB 挂掉时评论本身也写不进去。

## 二、建议的最小修复（替代 outbox）

### 2.1 旁路写入并入主事务

把 `notify_*` 与 `_auto_hide` 移到**主事务内**（与评论/举报同一次 commit）。
理由：同库同事务，通知表写失败时评论也写不进去——这比"评论成功但通知静默丢失"更好，
因为后者是**不可观测的静默不一致**。

**需要保留的例外**：`bump_hot_score` 继续 best-effort（派生数据，可重算）。
但要给它加一条"失败计数"，避免长期静默失败。

### 2.2 失败必须可观测

现在 `except Exception: logger.warning(...)` 的写法，在容器日志里很容易被忽略。
改为：
- 保留 best-effort 的动作（目前只有热度）失败时**写入审计日志**
  （`AUDIT_SIDE_EFFECT_FAILED`），运营大盘的「待办」里能看到；
- 这样"静默失败"变成"可见的失败记录"，比 outbox 的重试队列更贴合当前体量。

### 2.3 举报自动处置的幂等与自愈

`_auto_hide` 目前只在"提交新举报"时检查阈值。建议改为：
- 把 `_pending_count` 检查与 `_auto_hide` 并入举报写入的**同一事务**；
- 这样"举报成功 = 处置判断已执行"，不存在"举报成功了但没判"的中间态。

## 三、5 个决策点（待确认）

### D1 是否做 outbox？

**推荐不做**。理由见 1.4：全部同库，没有跨系统投递。
替代：旁路写入事务化（2.1）+ 失败可观测（2.2）。

### D2 通知并入主事务的风险是否可接受？

**推荐接受**。通知表是单表 insert，与评论 insert 同源同库；失败概率同级。
若担心"通知写失败拖垮评论"，可退一步：通知失败时**不抛错**，但把失败写入审计
（即 2.2 的落库，而不是只写日志）。

### D3 失败落库还是只写日志？

**推荐落库到审计**（`side_effect.failed`）。理由：日志在容器里没人看；
审计已经能在运营大盘里被看见，且天然带时间线。

### D4 举报自动处置是否合并为单事务？

**推荐合并**。当前"举报成功、处置没生效"的窗口没有自愈路径。

### D5 是否保留 outbox 的触发条件？

**推荐写下触发条件，而不是留一个空 backlog 项**：

- 需要向**外部系统**投递（邮件、推送、Webhook、消息队列）；
- 单个请求内的旁路动作**耗时超过 100ms**（例如调用第三方接口），
  不能挂在请求线程上；
- 需要**重试**语义（外部系统短暂不可用）。

三条都不满足时，outbox 只是把简单问题复杂化。

## 四、拆批建议（若 D1~D4 按推荐）

**P1-82 旁路写入事务化**：
1. `create_comment` / `set_like` 的通知移入主事务；
2. `submit_report` 的阈值处置与写入合并；
3. `bump_hot_score` 失败写审计（不阻塞）；
4. 补测试：通知失败时评论回滚 / 处置与举报同成同败；
5. 契约无需改动（外部行为不变）。

**规模**：约 3 个文件、4 处事务边界、5~8 项测试。
