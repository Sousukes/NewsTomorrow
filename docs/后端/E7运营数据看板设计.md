# E7 运营数据看板 · 设计方案

> 状态：**方案已定**。来源：backlog E7「把 `/api/metrics`、源健康、审核量、命中趋势
> 做成管理端大盘页」。本轮先做现状核实，**核实结果与 backlog 原文有两处不一致**，
> 故先把结论写下来再谈实现。

## 一、先量：backlog 原文的两处不成立

### 1.1 `/api/metrics` 不能直接当大盘数据源

`/api/metrics` 是 **Prometheus 文本格式**的**进程级**指标（`toutiao_requests_total` /
`by_status` / `by_path` Top20 / `sources_unhealthy`），且走 `require_ops_access`
（`OPS_TOKEN`，未配置时生产直接 403）。

三个都对不上：

| backlog 的预期 | 实际 |
| --- | --- |
| 管理端页面能读 | 需要 `OPS_TOKEN`，而管理端页面用的是**用户会话**（`require_admin`） |
| JSON | Prometheus  exposition 文本 |
| 运营关心的业务量 | 进程请求计数，与"今天有多少内容、多少举报"无关 |

它存在的理由是给 Prometheus 抓（C5），**不是给页面渲染的**。两者应当分开：
运维指标继续走 `/api/metrics`，运营指标新建管理端端点。

### 1.2 后端已有举报复核端点，**前端零对接**

`GET /api/admin/reports` 与 `POST /api/admin/reports/{id}/resolve` 在 P1-65 就完成了
（契约也测过），但前端：

- `api/admin.ts` 里没有任何 reports 函数；
- 没有 `AdminReports.vue`，路由表里没有 `/admin/reports`；
- 「我的」页的管理入口没有这一项。

**后果：E5 的举报复核队列在产品里不可达**——用户能提交举报（P1-66 做了入口），
运营却看不到、也处理不了。这是比"少一个大盘页"严重得多的缺口。

因此本设计把「顺带补齐举报复核页」纳入范围（见 §四 D6）。

### 1.3 可复用的现成能力（不需要新写）

| 能力 | 位置 | 状态 |
| --- | --- | --- |
| 多源窗口汇总 | `feeds/health.py::summarize_many` | **已是单条 GROUP BY**（P1-19 专门为防 N+1 写的），`/api/admin/sources` 正在用 |
| 窗口天数收敛 | `feeds/health.py::window_days` | 超出保留期的窗口只会得到一片空白，不如给等宽窗口 |
| 搜索热词 | `search_stats.py::hot_terms` | 有 60s 缓存（D6），键 `hot_terms:{days}:{limit}` |
| 昵称待复核队列 | `routers/admin/nickname.py` | 已在用（`User.name_pending_review`） |
| 待复核举报队列 | `routers/admin/reports.py` | 后端完整，前端缺失（见 1.2） |

## 二、关键约束：按天分桶在哪种列上安全

大盘需要"命中趋势"这类按天分桶的聚合。P1-74 刚在这里栽过：
`rss_source_health_events.at` 被 D1-1 迁成 `DateTime` 后，
`substr(at, 1, 10)` 在 PG 上直接 `function substr(timestamp with time zone, ...) does not exist`，
而 SQLite 单测全绿——**只有契约检查（真实 PG）能暴露**。

核实全部时间列后：**全库只有 `rss_source_health_events.at` 是 `DateTime(timezone=True)`**，
其余（`sensitive_hits.created_at` / `nickname_hits.created_at` / `reports.created_at` /
`search_logs.created_at` / `comments.created_at` / `news.published_at` …）都是
`String(30)` 存 UTC ISO。对这些列做 `substr(col, 1, 10)`：

- PG 的 `substr(varchar, int, int)` 与 SQLite 的 `substr(X, Y, Z)` 行为一致（都 1 起始）；
- 写入侧是 `now_str()`（UTC aware），前缀就是 UTC 日期，**不涉及会话时区**。

所以命中趋势可以安全地走 SQL 侧 `GROUP BY`。**但 D1-2 明确把 `hit_logs.*` 列进了
"按需再迁"的清单**——一旦迁移，这条查询会在 PG 上静默 500（与 P1-74 同款）。
因此本批必须带 PG 护栏测试（见 §五），让迁移发生时先红在测试上，而不是红在生产上。

## 三、端点设计

```
GET /api/admin/dashboard?days=7
```

单个聚合端点，返回 5 个板块。**不拆成 5 个端点**（D1）：

- 大盘是一次性渲染的面板，拆 5 个就是 5 次往返 + 5 个 loading 态 + 5 个错误态；
- 单端点才能保证**同一时间口径**——否则页面会出现"总量按 7 天、趋势按 30 天"的割裂，
  而这种割裂在运营眼里就是"数字对不上"；
- 每个板块的数据量都很小（计数 + 少量点 + Top N），不存在响应过大问题。

```jsonc
{
  "days": 7,
  "generatedAt": "2026-10-20T06:00:00+00:00",
  "content": {                     // 存量规模（不随 days 变）
    "news": 491, "newsHidden": 12, "comments": 340,
    "users": 88, "sources": 14, "sourcesEnabled": 12
  },
  "todo": {                        // "系统在等人"的队列
    "reports": 3,                  // status = pending
    "nicknameReviews": 2           // users.name_pending_review
  },
  "sourceHealth": {                // 窗口内最值得关注的源（D3）
    "windowDays": 7,
    "unhealthy": 2,                // 有失败且成功率 < 100% 的源数
    "worst": [                     // 按失败率倒序取 Top 5
      { "key": "...", "name": "...", "attempts": 40, "ok": 12,
        "failed": 28, "rate": 0.3, "avgItems": 18.5, "lastFailAt": "..." }
    ]
  },
  "moderation": {                  // 窗口内的治理量 + 命中趋势（D4）
    "newsHidden": 5, "commentsHidden": 9,
    "hits": { "sensitive": 34, "nickname": 7 },
    "hitsTrend": [ { "date": "2026-10-14", "sensitive": 4, "nickname": 1 } ]
  },
  "search": { "hot": [ { "term": "新能源", "count": 12 } ] }
}
```

三条边界：

1. **趋势只给窗口内的点，列表只给 Top N**（`worst` 5 条、`hot` 10 条）——
   大盘是概览，不是报表；要看全量去对应管理页。
2. **`generatedAt` 一律 `iso_utc()`**：SQLite 的 DateTime 读回不带时区，
   直接出响应会让双端格式不一致（P1-19 立过的规矩）。
3. **免 `total`**：计数就是计数，不做分页也不做"加载更多"——这个端点没有列表语义。

## 四、决策点

| # | 决策 | 取值 | 依据 |
| --- | --- | --- | --- |
| D1 | 单端点 vs 多端点 | **单端点** `/api/admin/dashboard` | 见 §三 |
| D2 | 时间口径 | **单一 `days`**，默认 7、上限 30（复用 `window_days`） | 30 < 命中日志保留期 90 < 搜索日志保留期，任何板块都不会拿到"超保留期的空白窗口" |
| D3 | 源健康 | **复用 `summarize_many`**，Python 侧按失败率排序取 Top 5 | 源数量级是十位数，全量取回再排序无压力；新写一份就会与 `/api/admin/sources` 漂移 |
| D4 | 命中趋势分桶 | **SQL 侧 `GROUP BY substr(created_at,1,10)`** | 这些列是 `String(30)`（§二），与 P1-74 的 DateTime 列不同；**必须配 PG 护栏** |
| D5 | 缓存 | **不缓存** | 管理端大盘低频（一天几次），缓存收益极小；而审核量是运营**决策依据**，陈旧比慢更糟。与 P1-62「热门列表评估后刻意不做」同款决策 |
| D6 | 范围 | **顺带补齐举报复核页**（前端） | 见 §1.2：唯一"系统在等人"的队列在产品里不可达；大盘的待办数字点不动的话运营价值减半。同源项一起还（backlog 规则 4） |

## 五、测试（含两条护栏）

功能测试之外，两条**护栏**是本批的重点：

1. **PG 护栏（对应 D4）**：`TestDashboardOnPostgres` 直连 PG（`TEST_PG_URL`，
   CI 的 postgres service 已在同一 job 内，P1-74 已接线）跑一遍趋势查询。
   它防的是"D1-2 把 `hit_logs.*` 迁成 DateTime 后 `substr` 在 PG 上 500"——
   迁移发生时会先红在测试上。已按 P1-74 的先例做**反向验证**（换回 substr 前确认红）。
2. **口径护栏**：`todo.reports` 只数 `status = 'pending'`（自动软隐藏也只算 pending，
   见 `app/reports.py`）；`content.news` 与 `newsHidden` 必须分开数——
   只数可见数会让"下架了多少"永远看不出来。

其余覆盖：单端点返回全部 5 板块、`days` 越界收敛（0 / 负数 / 超 30）、
免登录 401 / 非管理员 403、空库不炸（所有板块给 0 / 空列表而非报错）、
`worst` 的顺序（按失败率倒序，不是成员包含）、`hitsTrend` 按天升序且两序列齐全、
mock 与契约同步。

## 六、拆批建议

1. **P1-76（E7-a 后端）**：`app/metrics.py` 聚合模块 + `routers/admin/dashboard.py`
   端点 + 测试（含 PG 护栏）+ mock + 契约。
2. **P1-77（E7-b 前端）**：`AdminDashboard.vue` 大盘页 + `AdminReports.vue` 举报复核页
   + `api/admin.ts` 补 reports/dashboard + 路由与「我的」页入口 + 测试。

## 七、刻意不做

- **不做图表库**：趋势用最简单的行内条形/数字呈现（管理端是内部工具，
  引一个图表库的收益不抵它的体积与暗色模式适配成本）。若后续要折线图再评估。
- **不做实时推送**：大盘是"打开看一眼"的页面，进页面拉一次足够；
  WebSocket/轮询都是为"盯着看"设计的，与使用场景不符。
- **不把进程指标塞进大盘**：`/api/metrics` 继续服务 Prometheus（§1.1）。
- **不做自定义时间范围**：`days` 只有预设档（7 / 30）。自由日期选择会引入
  "起止日期 + 时区"的一整类问题，而运营的真实问题是"最近正常吗"。
