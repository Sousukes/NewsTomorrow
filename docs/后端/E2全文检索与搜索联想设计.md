## 一、现状核实（均已读代码确认）

比 backlog 描述的乐观——**搜索不是从零开始**，缺的是三块：

| 已有 | 依据 | 缺口 |
| --- | --- | --- |
| 标题/摘要 ILIKE 召回 + `pg_trgm` 分层相关度排序 | `routers/news.py::_search_ranked`（P1-11，权重经真机中文查询验证） | **正文未入召回**：E1 已落 `content`，但召回条件只有 `title`/`summary`，「只出现在正文里的关键词」搜不到 |
| 热搜榜（真实统计 + D6 二级缓存 + 30 天清理 + 用户去重） | `app/search_stats.py`、`GET /news/search/hot` | 热词**只能看不能输入时用**：没有联想，输错一个字（"暴雨兰色"）就只能拿到 0 结果 |
| 本地搜索历史（按账号隔离、可单删/清空） | `views/Search.vue`、`stores/user.ts` | 输入框无实时建议，历史词要先进二级页才能点 |
| 搜索 offset 分页 + `count()` | `search_news` | 深分页 O(offset)（B2 改造时搜索未纳入 keyset） |
| 零结果空态 | `views/SearchResults.vue` | 只有一句"换个关键词"+「返回首页」，**没有热搜/纠错入口**——用户被留在死路 |

> 附带发现：`SearchResults` 零结果里的「返回首页」按钮是 P1-69 修掉的 `EmptyState`
> 默认插槽丢按钮的受益者之一——那个 bug 让 ~10 个视图的空态动作全部失效。

## 二、方案范围（本批要做）

1. **正文入召回**（PG + trgm 路径）：新增最低一档权重，标题命中仍严格压过正文命中；
2. **搜索联想接口** `GET /api/search/suggest`：输入即出建议，含**纠错**能力；
3. **前端输入联想**：debounce + 代际守卫 + 点击直达；
4. **零结果引导**：给热搜词与「试试搜」入口，不再只有「返回首页」。

## 三、4 个决策点（已确认）

> 四条均取推荐值。以下每条末尾的「✅ 定案」是最终取值，实现以之为准。

### D1 联想的数据源：三源合并还是两源？

| 源 | 说明 | 代价 |
| --- | --- | --- |
| **热搜词前缀** | `search_logs` 近 7 天聚合，前缀匹配 | 复用 `hot_terms` 口径，零新增查询 |
| **标题前缀/包含** | 资讯标题是编辑质量最高的文本，`ILIKE` 前缀召回 | 复用 `ix_news_title_trgm` 索引 |
| **`search_logs` 相似词（纠错）** | 对**别人真实搜过的词**做 `similarity` 排序 | 关键：纠错有依据，不靠拼音/编辑距离瞎猜 |

**推荐三源合并**。理由：中文纠错不能靠编辑距离（"暴雨" vs "暴雨"打错成"bao yu"是另一回事），
但**用户经常搜错同一个词**——`search_logs` 里天然沉淀着大量"错词 → 正确词"的邻居关系。
例如有人先搜「新能源汽吃」0 结果，再搜「新能源汽车」，日志里两个词都是真实存在的，
把前者与后者按相似度关联即可给出纠错建议。这是本项目**已经握有**却没用起来的数据。

**不做**：拼音纠错（需引入 pypinyin，超出"零新依赖"的边界）、语言模型纠错。

> ✅ **定案：三源合并**（hot + title + correct）。

### D2 正文是否入召回？

**推荐入，但遵守三条界线**：

1. 权重最低（`title(100) > summary(10) > content(1)`），保证"标题命中的那篇"仍排第一；
2. **不给 `content` 建 trigram 索引**：正文单条可达 8000 字（E1 上限），GIN 索引体积
   与维护代价都不可接受；当前数据量级（数百条）下 `ILIKE` 全表扫描是毫秒级，
   明示"数据量上到万级需换方案（如独立索引/外部引擎）"；
3. **SQLite/fallback 路径不加**：该路径的存在意义是"无 trgm 时也能搜"，
   再加正文会把兜底路径的扫描面扩大数倍，且排序口径与 PG 不对称。

> ✅ **定案：入召回**，权重 `content(1)`，**不建 trigram 索引**，**SQLite/fallback 路径不加**，
> 并在代码注释里写明「万级数据量需换方案」。

### D3 搜索分页是否改 keyset？

**推荐不改**，把取舍写进文档：搜索排序的 `score` 是浮点表达式，keyset 需要把
`(score, published_at, id)` 三元组编码进游标，且每次续页都要**重复计算整串相似度表达式**
（否则比较基准不同）。收益只有"深分页不再 count()"，而搜索结果的翻页深度现实中极少超过 3 页。
成本（游标复杂度 + 浮点精度取舍 + 三条路径各自实现）明显高于收益。

> ✅ **定案：保持 offset + count**，取舍已记录于本节，不另开债（不是"忘了"，是"算过不做"）。

### D4 联想的交互形态？

**推荐输入即联想**（debounce 300ms + 代际守卫，点击直接带词进结果页），
并遵守三条：

- 联想请求**不写** `search_logs`（只有真正提交搜索才计入——否则边打字就污染热搜榜）；
- 未登录也可用（热搜词公开；相似词来自公共日志，不含用户隐私字段）；
- 空输入不请求，显示热搜榜（已有区块复用）。

> ✅ **定案：输入即联想**（debounce 300ms + 代际守卫），**联想不写 `search_logs`**。

## 四、接口契约

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/search/suggest?q=&limit=` | —（可选带 token）。`limit` 默认 8、上限 20。返回 `{ list: [{ term, kind, hitCount }], keyword }`；`kind` 取 `hot`（热搜邻居）/ `title`（标题）/ `correct`（纠错） |

- **去重与排序**：同一 `term` 只出现一次，优先级 `hot > correct > title`（被很多人搜过的词，
  比标题前缀更可能是用户真正想找的）；同 `kind` 内 `hitCount` 倒序、`term` 字典序兜底（确定性）。
- **不返回资讯内容**：联想只要词，不要顺带把标题当结果返回——那是搜索列表的职责，
  混在一起会让"选词"和"看结果"两件事互相干扰。
- 空 `q` → `{ list: [], keyword: '' }`（200，不报错）。

## 五、前端交互

- `views/Search.vue`：输入框下方浮现建议列表（300ms debounce；代际守卫丢弃过期响应）；
  键盘回车仍走原「提交搜索」；点建议 = `go(term)`（复用现有本地历史写入与跳转）。
- `views/SearchResults.vue`：零结果时给出「试试热搜」词条 + 「换个关键词」回搜索页，
  「返回首页」保留（P1-69 修好之后它终于能显示了）。
- `api/news.ts`：`fetchSuggestions(q, limit)`；mock 分支由种子数据派生（保持离线可演示）。
- `stores/news.ts`：`search` 不变（召回扩展在 API 层完成，前端无感）。

## 十、实现备注（P1-70）

### 纠错判据：相似度 **或** 编辑距离 ≤ 1（对设计的一处偏离）

设计原文是「对别人真实搜过的词做 `similarity` 排序」。实现后**排序键仍是相似度**，
但「是否属于错字」的判定改成了两条判据取**或**。依据全是量出来的：

| 现象 | 数据 |
| --- | --- |
| 三元组必须做 pg_trgm 的边界补齐 | 不补齐时「近期词」与「近期祠」三元组完全不相交，相似度恒为 0，短词纠错整体失效 |
| 补齐后短词错一个字相似度很低 | 「暴雨蓝色」vs「暴雨篮色」= 2/8 = **0.25**，过不了 0.3 门槛 |
| 但门槛降到 0.25 会放误报 | 「中国人民」vs「中国银行」共享 `  中` ` 中国`，也是 0.25，却不是错字关系 |

于是引入**编辑距离 ≤ 1**：它精确对应「打错 / 打多 / 打漏一个字」，而
「中国人民 / 中国银行」距离为 2，两条判据都不放行。相似度继续负责长词场景与排序。
两条判据缺一都会漏，所以是**或**而不是替换。

### 其余三条实测确认

- **D2 正文**：权重 1 后「标题命中仍排第一」在真实 PG 上成立；正文**不计 similarity**
  （无索引可吃，会让每条 8000 字正文都跑一遍三元组计算）。
- **D3 分页**：保持 offset + count，取舍已写在 §三，不是遗漏债。
- **D4 交互**：联想不写 `search_logs` 已由契约盯住（用不同 `days` 读两次热搜，
  绕开 D6 的 60s 缓存——同一个键的第二次读会命中缓存，断言会变成恒真）。

### 顺带发现（不在本批范围）

开发库 `content` 有 200/491 条非空，但长度普遍只有 12~85 字——**E1 的正文抓取
质量偏弱**，正文召回的实际收益被它压住了。属 E1 的账，未擅自动手。
