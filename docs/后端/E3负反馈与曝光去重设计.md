## 一、现状核实（均已读代码确认）

**两个缺口都不存在，是净新增，没有可复用的近亲。**

| 项 | 现状 | 证据 |
| --- | --- | --- |
| 负反馈 | 前后端**零入口**。`channel_preferences` 只吃收藏（3×）与浏览（1×）两个**正向**信号 | `grep -rn "不感兴趣/dislike" src/` 无结果；`ranking.py::channel_preferences` 只有 fav/hist 两个 JOIN |
| 曝光去重 | 无。列表接口不排除用户已看过的内容；`user_history` 只记**点击**，不记曝光 | `list_news` 的过滤只有 `channel` 与 `hidden`；`related_news` 里的 `seen` 集合只是**单次请求内**防重 |
| 相邻能力 | `user_history`（浏览历史，上限 50，按账号隔离）与 E5 举报表都在，但语义不同：历史是"我点过什么"（用户主动、要展示），曝光是"系统给我看过什么"（系统被动、用于去重） | `routers/me.py::HISTORY_MAX`；`models.py::Report` |

**核心事实**：`for-you` 排序目前**只有油门没有刹车**——收藏、浏览、关注（E6b 未接入排序）、热度全在加分，而用户对一条内容不满时唯一的出口是刷新页面。信息流产品里这通常表现为"越用越窄，且无法自救"。

## 二、方案范围

1. **负反馈**：单条「不感兴趣」+ 来源「减少该来源」两档，作用于 for-you 排序；
2. **曝光上报与去重**：曝光按进入视口判定、批量上报、保留期清理，for-you 排除已曝光；
3. **入口**：卡片角标（负反馈）+ 详情页更多菜单（负反馈 + 举报并列）。

## 三、5 个决策点（待确认）

### D1 负反馈的粒度：只做单条，还是加来源级？

| 方案 | 内容 |
| --- | --- |
| A. 只做单条 | 每条一个"不感兴趣"，踩了就不再出现在 for-you |
| B. 单条 + 来源（推荐） | 额外提供「减少该来源内容」：把该来源在 for-you 的分值乘一个衰减系数 |

**推荐 B，但来源级用衰减而非硬过滤**。理由：
- 用户说"不感兴趣"时，**多数场景指的是源**（"这个号整天发广告"），只给单条等于让他连踩 20 次；
- 但不能硬过滤来源：硬过滤后用户无法感知"被屏蔽了多少"，且误操作不可恢复——他只会觉得"内容怎么变少了"。衰减（推荐 0.3）让该来源仍以小概率出现，用户能持续确认效果并随时取消。

### D2 曝光的判定：渲染即算，还是进入视口才算？

**推荐进入视口 ≥ 50% 且停留 ≥ 500ms** 才算曝光。理由：
- 无限滚动会预渲染下方若干屏，**渲染 ≠ 被看到**。用渲染判定会把用户根本没扫到的内容计为已曝光，去重后信息流会明显变空；
- 停留阈值过滤"快速滑过"：滑过说明不感兴趣，但也不构成"看过"。
- 复用现有 `IntersectionObserver`（`useInfiniteList` 已在用），不引新依赖。

### D3 曝光存哪：新表，还是复用 `user_history`？

**推荐新表 `user_exposures`**，三条理由：

1. **语义相反**：历史是用户主动行为（要展示、可清空、上限 50），曝光是系统被动记录（不展示、自动清理）。混表会让"浏览历史"任意拉长到几百条；
2. **生命周期不同**：曝光按保留期清理（推荐 7 天），历史不清；
3. **写入模式不同**：曝光是批量追加，历史是单条 + 上限裁剪。

模型上不建 FK 到 news（与 `reports`/`user_follows` 同处方：目标被清理后记录仍可留存，去重时 LEFT JOIN 自然过滤）。复合主键 `(user_id, news_id)` + `exposed_at` 可更新（重复曝光刷新时间，避免同一条在保留期内反复计数）。

### D4 去重的强度与范围：过滤谁？哪些排序生效？

**推荐：仅 for-you 完全过滤已曝光；latest / hot 不过滤**。理由：
- for-you 是"给你挑的"，推己所不欲即噪声；
- **latest 是时间流，过滤会让"最新"漏内容**——用户按时间戳理解这一列，缺一条比重复一条更难解释；
- hot 同 latest（热榜是观察窗口，不是个人流）。

同时给一条**探底保护**：若过滤后不足一页且已曝光集合占总库比例过高（如 > 60%），当次不过滤，并在响应里带 `dedupRelaxed: true` —— 否则新用户/小库场景下会出现"关注流一样的天花板"（关注流那次是返回空页，这里是返回空页的变体）。

未登录时**用同一套逻辑落到 localStorage**（与 marks 的匿名命名空间同一处方，账号隔离、登出不清空、登录时采纳）。否则未登录用户完全看不到这个功能，而它恰恰是拉登录的好理由。

### D5 曝光上报的批量策略：逐条、定时、还是离场 flush？

**推荐：累积到 10 条或 5 秒即上报，页面隐藏/卸载时强制 flush**。
理由：曝光是**高频写**（一屏 20 条，翻两页就 60 条），逐条 POST 会把信息流浏览变成 60 次写入请求；攒批后一次请求 10 条，写放大降低一个数量级。`visibilitychange` + `pagehide` 兜底，避免用户直接划走丢了最后几条。

失败静默重试一次，仍失败丢弃——曝光丢失的代价只是"这条可能重复出现一次"，远小于阻塞浏览。

## 四、接口契约

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/me/exposures` | ✅。body `{ ids: string[] }`（1~50）。**幂等**：重复上报只刷新 `exposed_at` |
| GET | `/api/me/dislikes` | ✅。返回 `{ news: [...], sources: [...] }`（负反馈集合） |
| POST | `/api/me/dislikes` | ✅。body `{ newsId?, sourceKey? }`（二选一，都缺或都给 42207）。**幂等**：同一目标重复踩只更新时间 |
| DELETE | `/api/me/dislikes/news/{id}`、`DELETE /api/me/dislikes/sources/{key}` | ✅。取消负反馈（幂等） |

- `GET /api/news?sort=for-you` 响应新增 `dedupRelaxed: boolean`（客户端可据此显示"已看内容较多，本次未去重"的提示，也可直接忽略）。
- 错误码：**42207** 复用为"负反馈参数非法"（与关注上限同一段号，都是"输入集合不合法"）。
- **负反馈与举报严格分离**：举报走 E5 的 `/api/reports`，不在这里留任何入口——把"我不爱看"和"这内容违规"混成一个字段，运营侧就无法区分两者。

## 五、前端交互

- `NewsCard` 右下角「×」：点击弹轻量菜单（不感兴趣 / 减少该来源 / 举报），与关注、收藏等低频负向操作一致，**不进主操作区**。
- 曝光：`useExposure` 组合式函数（IntersectionObserver + 50% + 500ms + 攒批），首页/视频页列表复用。
- 已曝光内容：for-you 里不出现；用户点进详情后返回，该条从列表中**原地移除**（而不是留一个"已读"样式——读过的还占位是噪声）。

## 六、刻意不做

- **不做跨会话的"已读"标记样式**（历史上有产品这么做）：与浏览历史职责重叠，且去重后大部分场景已不需要；
- **不做负反馈的自动降级阈值**（如"踩 3 个某来源就永久屏蔽"）：单次衰减已足够，自动升级会让用户失去控制感；
- **不把曝光用于热榜统计**：曝光量会随用户量线性增长，混进热度会让热榜变成"谁被推得多谁热"（马太效应），热度只看互动。

1. **P1-72 后端**：迁移 0034（`user_exposures`）/ 0035（`user_dislikes`）或合并为一个 0034；
   `/api/me/exposures` 批量上报、`/api/me/dislikes` 三件套、for-you 去重 + 探底保护、负反馈入排序；
2. **P1-73 前端**：`useExposure` 组合式函数、卡片负反馈菜单、详情页已读移除、本地匿名曝光、mock 与契约同步。

## 八、验收标准

- for-you 下拉刷新后，**已点击/已曝光的内容不再出现**；latest / hot 仍完整；
- 点「不感兴趣」后该条立即消失，刷新后不回来；
- 踩某来源 1 次后，该来源在 for-you 的出现频率明显下降但**不完全消失**；
- 曝光批量上报：翻 3 页不超过 3 次请求；直接划走页面不丢最后几条（`pagehide` flush）；
- 未登录用户同样生效（localStorage），登录后匿名曝光被采纳；
- 曝光接口失败不影响浏览；负反馈失败时界面回滚并提示；
- 迁移链（0034）在 PG / SQLite 双向通过，`alembic check` 无漂移。

## 十一、实现备注（P1-73）

### 未登录的曝光：本批不落 localStorage（记为 E3-a）

设计 §三 D4 写过「未登录时用同一套逻辑落到 localStorage，登录时采纳」。
实现时**只做了前半句的替代方案**：未登录直接不上报。

- 理由一：曝光去重由**服务端**做，匿名上报到 `/me/exposures` 只会吃 401，
  落本地也无处消费（除非再在客户端实现一份去重——那就成了第二份实现）。
- 理由二：完整的"登录时采纳"需要改 `stores/user.ts` 的 marks 采纳流程，
  单独做又会多出一套命名规则与作用域约定。
- 匿名用户的实际收益由**已读原地移除**承担：本地生效、不需要账号。

### 判定参数落在前端而不是后端

视口比例与停留时长是**客户端事实**（后端不知道用户有没有滚到那条），
所以 50% / 500ms / 攒批这三个数写在 `composables/useExposure.ts`，
后端只负责"收到一批 id 就记下"。这条边界不划清的话，很容易演变成
"前端每滚一下就打一个接口"。
