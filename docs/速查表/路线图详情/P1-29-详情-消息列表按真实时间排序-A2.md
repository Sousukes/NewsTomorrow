#### P1-29 详情：消息列表按真实时间排序（A2）
**问题**：互动消息 id 是 `msg_{uuid4hex}`（随机串），列表却按 id 倒序排、
游标用 id 比较——顺序与真实时间无关，keyset 语义失效。

**排序与分页**

```
ORDER BY coalesce(created_at, '') DESC, id DESC
游标 = 上一页末条的 id（格式不变）
  → 服务端按该 id（带可见范围过滤）回查锚点行的 created_at
  → 取 (key < 锚点key) OR (key = 锚点key AND id < 锚点id) 的一页
```

**四个设计选择**

| 选择 | 理由 |
| --- | --- |
| `created_at` 可空、不回填 | 存量行无可信时间源（`time` 是「1小时前」相对文案），编造时间比没有更糟 |
| `coalesce(created_at, '')` 兜底 | 空串 DESC 垫底 → 存量行自然沉底；PG/SQLite 一致（`NULLS LAST` 两者语法支持度不同，且 SQLite 老版本不支持） |
| 单列索引 | 可见范围是 `user_id = X OR user_id IS NULL`（OR），`(user_id, created_at)` 复合索引走不了；单列索引服务 ORDER BY，避免每页全表排序 |
| 游标仍是 id | 前端零改动、老游标不失效；锚点键以库中权威行为准，客户端改游标也翻不出可见范围 |

**踩坑（ORM 默认值的陷阱）**：测试想造「存量 NULL 行」时用
`Message(created_at=None)` 构造——**模型 `default=now_str` 在值为 None 时
照样触发**，插进去的是「现在」的时间戳，排序断言全反。真正的存量行只能用
raw SQL 插（绕过 ORM 默认值）。这个坑值得记住：**ORM 的显式 None ≠ 数据库 NULL**
（有列级默认值时）。

**测试**：`TestMessageOrdering` 6 项（时间倒序/存量 NULL 沉底/同秒 id 决胜/
翻遍全表不重不漏且收敛/他人消息 id 当游标回第一页/模型默认值自动写入）、
`test_migrations.py` +1（0026 列可空 + 单列索引断言）。
