#### P1-20 详情：资讯审核与下架
**补的缺口**：抓到错误/侵权/待核实的内容，此前只有删库一条路——删了连证据都没了，
运营不敢动手；而没有「先下线再核实」这个动作，内容风险暴露的时间就没有上限。

| 设计 | 规则 |
| --- | --- |
| 软下架非硬删 | `news` +3 列（迁移 **0020**）：`hidden`（非空、`server_default=false`）/ `hidden_at` / `hidden_reason`；行还在，只是对外不可见 |
| 理由必填 | trim 后非空、≤300；空理由 42200。**「留痕是准入条件」**——没有理由的下架在审计上不可辩护 |
| 后审核模式 | **不改内容管线**：RSS 按 id 去重、热度重算仍算下架行；**恢复即实时可见**，不需要重新抓取 |
| 公开同码 404 | 列表/详情/搜索/相关/评论五路过滤；已下架与不存在**同为 40400**（不对外泄露「曾被下架」）；管理端 **40404** 区分，方便排障 |
| 不建索引 | `hidden` 命中面积极小（已下架永远是少数），索引只拖慢每轮写入 |
| 幂等 | 重复下架**不覆盖原理由、不重复记审计**；恢复清空 reason/at（防张冠李戴——恢复时不留旧理由，下条再下架必须重新填） |
| 置顶 | 走 `PATCH /admin/news/:id` 字段级 diff 审计（与 P1-15 源更新同范式，**无变化不记**） |
| 游标分页 | 管理端列表 `[published_at, id]` base64url(JSON) keyset；坏游标 40003；`total` 始终返回（运营要看「共 N 条」） |

**接口**（均需登录 + 具备管理能力）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/news` | `status=all\|visible\|hidden`（默认 all）、`keyword`（标题/摘要，≤50）、`channel`、`limit`（1–100）、`cursor`；返回 `{list, total, hasMore, nextCursor}` |
| GET | `/api/admin/news/:id` | 管理端详情（含 hidden 三件套）；不存在 40404 |
| POST | `/api/admin/news/:id/hide` | 请求体 `{reason}`；**理由必填**（空 42200、>300 42200）；幂等 |
| POST | `/api/admin/news/:id/restore` | 恢复；幂等；清空 `hidden_at`/`hidden_reason` |
| PATCH | `/api/admin/news/:id` | 仅 `isTop`（**驼峰**）；无变化不记审计 |

**审计新动作**

| action | 触发 | detail 结构 |
| --- | --- | --- |
| `news.hide` | `POST /admin/news/:id/hide` | `{ reason, title }` |
| `news.restore` | `POST /admin/news/:id/restore` | `{ title }` |
| `news.update` | `PATCH /admin/news/:id`（**仅当 isTop 有变化**） | `{ changes: { isTop: [旧, 新] }, title }` |
