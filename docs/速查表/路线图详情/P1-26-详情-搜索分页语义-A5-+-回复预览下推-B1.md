#### P1-26 详情：搜索分页语义（A5）+ 回复预览下推（B1）
两个都来自架构审查的 P0 清单，改动小但**用户可直接感知 / 有明确性能悬崖**。

**A5 · 搜索结果「加载更多」**

| | 修复前 | 修复后 |
| --- | --- | --- |
| 结果集 | `results.value = res.list`（整段替换） | 第 1 页替换；后续页**追加 + 按 id 去重** |
| 终止条件 | `results.length >= total` | 服务端 **`hasMore`** |
| 按钮显隐 | `results.length < total` | `hasMore` |

「按钮文案写着 `加载更多（2/5）` 却把列表换成第 2 页」是典型的**文案与实际行为不符**——
用户侧表现为「翻页后前面的结果没了」。

**B1 · 回复预览的 LIMIT 下推**

```sql
-- 修复前：rn 算出来了，但 WHERE 不能引用窗口列 → 只能在 Python 侧截断
SELECT *, row_number() OVER (PARTITION BY root_id ORDER BY created_at, id) AS rn
FROM comments WHERE root_id IN (...)          -- 捞回全部回复

-- 修复后：子查询内算 rn，外层过滤 → DB 只返回每组前 2 行
SELECT ... FROM (
  SELECT *, row_number() OVER (PARTITION BY root_id ORDER BY created_at, id) AS rn
  FROM comments WHERE root_id IN (...) AND is_deleted = false AND hidden = false
) AS anon_1 WHERE anon_1.rn <= 2
```

ORM 侧用 `aliased(Comment, subquery)` 把子查询列映射回实体。已删除 / 已隐藏的过滤
写在**子查询内部**——下推后漏掉这些条件会让预览露出不该可见的内容，故有对应回归。

**测试**：后端 `TestCommentReplies` 9 → **12 项**（`rn <= N` 必须出现在**实际执行的 SQL** 里、
30 条回复时预览仍是最早 2 条且 `replyCount` 计全部、预览跳过已删除与已隐藏）；
