#### P1-22 详情：评论治理（软隐藏 / 恢复）
**补的缺口**：评论是 UGC 里风险最高的一类——广告、辱骂、剧透、未核实传闻。
此前只有软删除一条路（`DELETE /news/:id/comments/:cid`，作者侧、不可逆）：
删了上下文全丢、作者看不到「为什么没了」、运营也不敢轻易动手。
缺一个「先隐藏再核实」的中间态，评论风险的暴露时间就没有上限。

| 设计 | 规则 |
| --- | --- |
| 软隐藏非硬删 | `comments` +3 列（迁移 **0022**）：`hidden`（非空、`server_default=false`）/ `hidden_at` / `hidden_reason` |
| 与 is_deleted 分工 | `is_deleted` = 作者侧软删除（作者自己删，**不可恢复**）；`hidden` = 运营治理（**可恢复**）。两条正交，查询条件互不干扰 |
| 理由必填 | trim 后非空、≤300；空/纯空白/超长一律 **42200**（schema 层 `Field(min_length=1, max_length=300)` + 非空白校验）。**「留痕是准入条件」**——没有理由的隐藏在审计上不可辩护 |
| 公开五路过滤 | 主列表 / 回复列表 / 评论计数 / 点赞 / 回复创建五路**实时**生效（无需等任何定时任务）；**主评论隐藏后其回复亦不可见**——回复失去语境，不裸露 |
| 双码分离 | 公开端已隐藏与不存在**同为 40401**（不对外泄露「曾被隐藏」）；管理端 **40405** 区分，方便排障 |
| 计数热度联动 | 隐藏使 `comment_count` −1（下限 0）、恢复 +1；`was_visible` 守卫——重复隐藏不会重复扣减 |
| 不建索引 | `hidden` 命中面积极小（已隐藏永远是少数），索引只拖慢每轮写入 |
| 幂等 | 重复隐藏**不覆盖原理由、不重复记审计**；恢复清空 reason/at（防张冠李戴——恢复时不留旧理由，下条再隐藏必须重新填） |
| 游标分页 | 管理端列表 `created_at DESC, id DESC` keyset，游标为上一页末条 id（明文）；`total` 始终返回（运营要看「共 N 条」） |

**接口**（均需登录 + 具备管理能力）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/comments` | `status=all\|visible\|hidden`（默认 all，**含已隐藏**）、`keyword`（正文 ILIKE，≤50）、`newsId`（**驼峰**，≤32）、游标分页；已软删除一概不返回 |
| GET | `/api/admin/comments/:id` | 管理端详情（含 hidden 三件套）；不存在 **40405** |
| POST | `/api/admin/comments/:id/hide` | 请求体 `{reason}`；**理由必填**（空/纯空白/超长 **42200**）；幂等 |
| POST | `/api/admin/comments/:id/restore` | 恢复；幂等；清空 `hidden_at`/`hidden_reason` |

**审计新动作**

| action | 触发 | detail 结构 |
| --- | --- | --- |
| `comment.hide` | `POST /admin/comments/:id/hide` | `{ reason, content（前 50 字）, newsTitle, userName }` |
| `comment.restore` | `POST /admin/comments/:id/restore` | `{ content, newsTitle, userName }` |
