## 批次 P1-9（2026-10-13）：RSS 源可配置化（路线图第 7 项）
- **问题**：RSS 源**硬编码**在 `app/feeds/sources.py` 的 `RSS_SOURCES` 列表里——
  新增 / 停用 / 调权重都要改代码并重新部署，运营无法介入。
  更隐蔽的是：**源是否还活着无处可见**——`fetch_source()` 失败时静默返回空列表，
  健康状态永远"正常"，源悄悄烂掉（改版、迁址、返回 HTML）也无人发现。
  本次同时把 **AIHOT**（`https://aihot.news/feed.xml`）加入内置源。
- **源从代码搬到表里**：
  - 新增 `rss_sources` 表（迁移 `0013_rss_sources`），**实际抓取读库**；
  - `BUILTIN_SOURCES` 退化为两个用途：**播种**（表为空时写入，新环境开箱可用）与
    **回退**（无数据库会话时单测/脚本仍可运行）；
  - **只在表为空时播种**——否则运营的停用/调权重会被下次启动覆盖；
  - `key` 作主键，同时是内置源与库记录对齐的依据（改内置源不会重复插入）。
- **新增管理接口 `app/routers/admin.py`**：列表 / 新增 / 局部更新 / 删除 / 重置（恢复出厂）。
  - 鉴权沿用 `ADMIN_PHONES` 白名单；**白名单为空 = 能力整体关闭（403）**，
    避免生产因配置疏漏而暴露管理接口；
  - **URL 协议白名单（仅 http/https）**：抓取器会真的请求该地址，必须挡住 `file://` 注入；
  - **局部更新不清空未传字段**；**停用优先于删除**（删除能力保留，加错源时确实需要）。
- **健康状态回写**：每轮抓取把 `last_status / last_error / last_item_count / last_fetched_at`
  写回源表。源变多后"哪个源挂了"是首要排障问题，靠翻日志很低效。
- **契约变更：抓取失败必须可辨识**（本次改动中最关键的一处）
  - `fetch_source()` 失败由「**静默返回空列表**」改为抛 `FetchError`。
    原因：空列表无法区分"源不可达"与"源正常但没有新条目"，健康状态就永远是 `ok`。
  - `_fetch_with_retry()` 重试仍失败则**向上抛**，由 `collect()` 记为该源故障
    （`ok=False` + 原因），**单个源失败不影响其他源**，整轮抓取也不会因此抛错。
  - `NotModified`（304，内容未变更）是**唯一**返回空列表的正常路径。
  - 副作用：源正常但解析出 0 条（多半是改版/返回 HTML）现在也会被标记为故障——
    这正是我们想看见的信号。
- **新增 AIHOT 源**：`aihot_picks`（AI 垂直资讯，`tech` 频道，权重 9）。
  真实抓取验证：**20 条**入库、健康状态 `ok/20`。
- **错误码**：`40902`（源 `key` 已存在，**与 `40901`「手机号已注册」刻意分开**——
  同一码承载两种语义会让前端文案错配）、`40004`（源地址非 http(s)）、`40402`（源不存在）。

- **踩坑（写进测试注释，避免复发）**：
  - **`ADMIN_PHONES` 不能靠 `os.environ` 设置**：它是 `app.config` 的模块级常量，
    首次 import 即定稿；全量跑时 `test_api.py` 先导入（带自己的号段），
    本文件的 env 设置完全无效 → 症状是**整类管理接口用例 40301**，
    而**单独跑本文件却全绿**。改为 fixture 直接改模块绑定。
  - **本文件反复登录会触发限流**：同一 testclient IP 很快触顶，
    login 返回 `data=None`，报错点会指向莫名其妙的取值行 → 需 `RATE_LIMIT_ENABLED=false`。
  - **退避重试会让测试白等**：坏源每个重试 2 次 ≈ 2s，故 fixture 内 patch 掉 `time.sleep`。
