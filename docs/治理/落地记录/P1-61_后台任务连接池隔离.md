## 批次 P1-61（B5）：后台任务与 API 的连接池隔离

backlog 原文：「抓取与 API 同进程，共用线程池与连接池，长抓取挤压请求侧」。

## 先确认挤压是怎么发生的（不是"同进程"本身）

`_run_once` 的写法是**整个抓取周期只开一个 session**：

```python
with SessionLocal() as db:          # 占住一条池连接
    _try_lock(db, ...)              # advisory lock 绑在**会话**上，中途不能关
    run_ingest(db, ...)             # 里面发 N 个 HTTP 请求，各带超时
```

于是这条连接被占**几分钟**（`advisory lock` 依赖会话存活，不能改成"用完就还"）。
与 API 共用 `pool_size=5 + max_overflow=10` 时，抓取 + 热度重算能长期吃掉 2 条，
请求峰值就在 `pool_timeout`（30s）上排队。

**共享池不是"省资源"，而是把两种完全不同的占用时长混在一起**：请求是毫秒级，
抓取是分钟级。混池的后果是**后者决定前者的尾延迟**——而这类问题不报错，
只是"偶尔接口变慢"。

## 改了什么

1. **独立 engine + 独立会话**：`scheduler_engine` / `SchedulerSessionLocal`，
   `pool_size=2`（抓取 + 热度重算两个任务各一条）、`max_overflow=1`；
2. **独立 `application_name`**（`toutiao-scheduler`）：`pg_stat_activity` 里能一眼
   分出"连接是请求打上来的，还是抓取占着的"——没有这个，线上看到连接数偏高时
   根本无法归因；
3. **其余池参数原样保留**：`pool_recycle` / `pool_pre_ping` / `pool_use_lifo` 与 API 一致。
   漏掉 `pre_ping` 就会在服务端断开后拿到死连接，那种"偶发一条请求失败"最难查，
   不该因为拆池而丢掉（有测试钉住）；
4. `dispose()` **释放两个池**：只释放 API 池会留下后台连接，PG 端表现为 idle 慢慢堆积。

## SQLite 必须例外（否则测试全炸）

内存库靠 `StaticPool` 共享同一条连接才有数据可言；另建 engine 会得到一个**空库**，
症状是"表不存在"——根因却是池隔离。所以：

```python
scheduler_engine = engine if URL.startswith("sqlite") else create_engine(...)
```

这条也有测试钉住，防止有人"顺手"把 SQLite 也隔离了。

## 测试（10 项）

- SQLite 复用同一 engine；PG 拿独立小池；
- 后台任务的 `application_name` 与 API **不同**；
- 其他池参数（回收/探活/超时/LIFO）与 API **一致**；
- **真的建一次 PG engine**（`create_engine` 惰性、不连库，所以无 PG 也能跑）
  验 `pool.size()`：2 vs 5，且两个 pool 是不同对象；
- `dispose()` 释放两个池，SQLite 共享时**不重复释放**；
- 调度器模块用的是 `SchedulerSessionLocal`，且**没有残留** `SessionLocal` 引用
  （用错会话，池就白拆了）。

## 诚实边界

本批解决的是**连接池混用**；**进程内线程池**仍未分离（抓取占的是调度器自己的线程，
`BackgroundScheduler` 默认池与 FastAPI 的 anyio 线程池本就是两套，实测无共用）。
真正的进程级隔离（抓取独立工作进程）需要部署编排，属 backlog 未开项。
