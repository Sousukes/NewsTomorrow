## 为什么"顺带"补举报复核页

E5 的用户侧入口 P1-66 就做了（能提交举报），后端复核端点 P1-65 就做了、契约也测过，
但**前端从未对接**：没有 api 函数、没有页面、没有路由、没有入口。
结果是举报进了黑洞——运营看不到、也处理不了。

这比"少一个大盘页"严重：大盘的"待办 3"点进去什么都没有，数字就成了装饰。
所以本批把这条链路接通，并顺手补上它缺失的契约覆盖（此前 `/admin/reports` 零覆盖，
而前端现在要依赖它）。

## 六个实现要点

1. **后端补「被举报对象预览」**：只给 `targetId` 的话复核页无法判断——评论尤其致命
   （它没有独立公开页面，光看 id 无从下手）。列表与处置响应都带
   `targetTitle` / `targetSnippet` / `targetNewsId` / `targetMissing`，
   两类对象各**一条 IN 查询**（共 2 条），不做逐行查。
2. **`targetNewsId` 才是能跳的那个 id**：资讯填自身 id，评论填**所属资讯** id——
   前端据此跳到 `/news/{id}` 或 `/news/{id}/comments`。
3. **确认隐藏二次确认，驳回不确认**：隐藏让内容不可见（虽可恢复），驳回是恢复可见（安全方向）。
   破坏性操作要确认，恢复不需要——这条不对称是刻意的。
4. **每条待办都能点进"已经筛好的"队列**：`待复核评论` 跳到
   `/admin/comments?status=pending`（为此给该页加了 query 初始化）；
   只给数字不给出口，等于把运营挡在半路。
5. **趋势用行内条形，不引图表库**（设计 §七）：宽度按窗口**峰值**归一——
   否则小数字在长条旁边看不出变化；图上标了"数字为敏感词/昵称"。
6. **归一化要保住 null**：`Number(null) === 0` 会把"无成功轮次"（`avgItems: null`）
   抹成"平均 0 条"、把"无尝试"（`rate: null`）抹成"0% 成功率"——
   两者含义完全不同（前者显示 `—`、后者显示 `0%`）。为此单独加了 `nullableNum`。
   > 这条是**测试抓出来的**：首版用 `num()`，断言 `avgItems === null` 时拿到 0。

## 测试（+5 后端 / +38 前端）

**后端**（`tests/test_reports.py` +5）：资讯预览带标题且 `targetNewsId` 是自身、
评论预览带片段 + **所属资讯 id**、片段按 `PREVIEW_LEN` 截断并带省略号、
目标已删除时 `targetMissing=true`、处置响应与列表同形状。

**前端**（38 项）：
- `AdminDashboard.spec.ts`（11）：六板块齐全、单请求、成功率 null 显示 `—`、
  趋势条按峰值归一、三条待办各自跳到"已筛好"的队列、全 0 时明确说没有待办、
  无失败源/无命中/无热词三种空态文案、失败提示、非管理员不请求、时间窗切换与幂等
- `AdminReports.spec.ts`（17）：评论/资讯预览、评论跳所属资讯评论区、目标已删除文案、
  **确认隐藏二次确认**（首次不发请求）、驳回直接生效、确认态可取消、
  处理完移出待处理队列、筛选切换、按游标翻页、失败提示、权限与空态
- `api/admin.spec.ts`（6）：dashboard 带 days、脏值收敛为 0/空数组、
  **worst 保持后端顺序**（不在前端重排）、reports 由 nextCursor 推导、
  resolve 发 POST、非法 id 丢行不抛错
- `AdminComments.spec.ts`（2）：`?status=pending` 生效、未知档位回落 `all`
- `Profile.spec.ts`（2）：两名新入口可见可跳、非管理员看不到

> 写 spec 时踩到两个"测试静默无效"的坑：
> ① 全页找「驳回」会先命中筛选器的「已驳回」chip —— 点了 chip 自然没调接口，断言看起来像功能坏了；
> ② 两条测试行的预览文案相同时，"移出"与"没移出"看起来一模一样。两处都改成限定范围/互不相同的样本。
