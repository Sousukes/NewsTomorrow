## 批次 P1-56（2026-10-18）：前端覆盖率门槛（F4）+ 覆盖率基线盘点

后端在 P1-45 就有了 `--cov` 门槛（`.coveragerc` `fail_under = 91`），前端一直是
「跑测试但不管覆盖了多少」。本批补上对偶项，并**顺手量出真实基线**——那份基线
直接决定了 F5/F3' 该先补哪些。

## 关键设计：`all: true` 才是门槛

不打开 `all` 时，覆盖率**只统计被测试 import 过的文件**。后果是：

> 新增一个模块、不写任何测试 → 它不会被 import → **数字一点不掉** → 门槛形同虚设。

打开后未被导入的文件按 0% 计入。实测差别很大：

| | 参与统计文件数 | 语句 | 行 |
| --- | --- | --- | --- |
| 默认（只算 import 过的） | 47 | 78.64% | 81.79% |
| **`all: true`** | **62** | **71.93%** | **74.71%** |

多出来的 **15 个文件就是之前"看不见"的空洞**。

## 门槛与验证

阈值取实测下浮约 2 个点（与后端 `.coveragerc` 同策略：门槛防回退，不追求数字）：

```
statements 70 / branches 64 / functions 60 / lines 73
（实测 71.93 / 65.75 / 60.77 / 74.71）
```

**门槛必须验一次「真的会拦」**，否则设了等于没设。做法：把 `lines` 临时抬到 99，
确认 `ERROR: Coverage for lines (74.71%) does not meet global threshold (99%)`
且退出码 1；恢复后退出码 0。这比"配置写对了"的自我感觉可靠。

CI 里把 `npm run test` 换成 `npm run test:cov`（`vitest run --coverage`），
于是覆盖率不达标 CI 直接红。

## 覆盖率基线（F5 / F3' 的排序依据）

**0% 的 15 个文件**——注意其中三个是**安全/错误路径**，比"没测的展示页"严重得多：

| 文件 | 为什么值得先补 |
| --- | --- |
| `stores/stepUp.ts` | 二次校验（C10），安全相关，0% 意味着整条链路没测过 |
| `api/auth.ts` | 登录 / 刷新令牌的 API 层 |
| `components/ErrorBoundary.vue` | 错误兜底：崩的时候它若也崩，用户看到白屏 |
| `composables/useNewsDetail.ts` | 深链安全逻辑 |
| `components/StepUpDialog.vue` / `PhoneFrame.vue` | 交互组件 |
| `views/{Gallery,History,Messages,Search,Showcase,Videos}.vue` | 6 个无 spec 的视图（= F3' 剩余项） |
| `api/{comments,messages}.ts` | API 层 |

**非零但低**：`Favorites.vue` 10% / `ChangePassword.vue` 15.6% / `api/me.ts` 18.9%。

**结论（写进 backlog）**：F5 的优先级应按「安全/错误路径 > API 层 > 展示页」排，
而不是按文件行数或字母序——`stepUp.ts` 0% 的风险远高于 `Gallery.vue` 0%。
