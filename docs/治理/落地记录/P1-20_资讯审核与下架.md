## 批次 P1-20（2026-10-15）：资讯审核与下架（先下线，再核实）
- **背景**：抓到错误 / 侵权 / 待核实的内容，此前只有**删库**一条路——删了连证据都没了，
  运营不敢动手；而没有「先下线再核实」这个动作，内容风险的暴露时间就没有上限。
  用户选定本批（另两个候选：热度重算独立调度、评论治理）。
- **设计①：软下架非硬删**（迁移 **0020**：`news` + `hidden`（非空、`server_default=false`）/
  `hidden_at` / `hidden_reason`）。行还在，只是对外不可见——留痕、可恢复、可申诉。
  这是项目里第二处软删先例（第一处是 P1-2 评论），沿用同一套语义。
- **设计②：理由必填 = 留痕是准入条件**（trim 后非空、≤300，空则 42200）。
  没有理由的下架在审计上不可辩护——「谁为什么把它下了」必须能回答。
- **设计③：后审核模式，不动内容管线**。RSS 按 id 去重，下架的行不会被重复抓取覆盖；
  热度重算**仍算下架行**（它是派生数据，恢复后立即参与排序）；
  **恢复即实时可见**，不需要重新抓取——这是「软下架」对「删库」的结构性优势。
- **设计④：公开侧同码 404**。列表 / 详情 / 搜索 / 相关 / 发评论五路过滤，
  已下架与不存在**同为 40400**（不对外泄露「曾被下架」）；管理端 **40404** 区分，
  方便排障。**不给 `hidden` 建索引**——命中面积极小（已下架永远是少数），索引只拖慢每轮写入。
- **设计⑤：幂等语义**。重复下架**不覆盖原理由、不重复记审计**（运营连点两次不该产生噪音）；
  恢复**清空 reason/at**——防止张冠李戴（恢复时留着旧理由，下一条再下架会看到上一条的理由）。
- **设计⑥：置顶走 PATCH + 字段级 diff 审计**（沿用 P1-15 源更新范式，**无变化不记**）。
  管理端列表用 `[published_at, id]` base64url(JSON) keyset 游标（坏游标 40003，
  `total` 始终返回——运营要看「共 N 条」）。
- **审计新动作**：`news.hide`（detail `{reason, title}`）/ `news.restore`（`{title}`）/
  `news.update`（`{changes, title}`）——三动作都带标题，时间线里能认出是哪条。
- **前端**：新增 `/admin/news`（`views/AdminNews.vue`）——全部 / 可见 / 已下架三态 chips +
  关键词搜索（服务端筛选）、已下架行红 chip + 理由 + 下架时间、下架弹窗
  （**空理由前端拦截**「请填写下架理由（留痕是准入条件）」、≤300）、一键恢复、
  置顶开关（**乐观更新 + 失败回滚**）、游标「加载更多」、每行「历史」直达审计时间线；
  `api/admin.ts` 补 `fetchAdminNews` / `hideNews` / `restoreNews` / `updateNewsTop`
  （仅真实后端，**mock 模式一律拒绝**——与源管理同一立场，不伪造可变的审核数据）；
  行数据经 `toNews()` 归一化（缺 `id` 丢弃、hidden 三件套缺失按可见兜底、非法 `channel`
  回落 `recommend`）；入口在个人中心。
- **测试发现的真实 bug（前端）**：`AdminNews.vue` 的 `clearFilters()` 初版**没有重新拉取**——
  服务端筛选下清了筛选，列表停留在旧筛选结果上。修复：复位后调 `load()`。
  教训：服务端筛选的「清除」不只是状态复位，**必须触发请求**（客户端过滤才不会暴露这个 bug）。
- **踩坑（测试写法）**：① 「可见筛选下架后行移除」的断言被 toast 文案
  「已下架《某 AI 新品发布》」命中而误报——改为按 `.admin__name` 断言剩余行列表；
  ② 「恢复已下架资讯」用例里 `restoreNews` mock 返回值必须**带上同一行的 id**，
  否则按 id 找不到行；③ 「加载更多」按钮不存在时 `.exists()` 报 TypeError——
  改 `findAll('button').some(...)`；④ 按钮全等匹配（`btn(w, '下架')`）防「确认下架」误配。
- **mock 后端同步**：五端点 + **已下架种子资讯**（否则 mock 下永远看不到「已下架」分支，
  同类静默失效 P1-18 踩过）+ 公开四路过滤对 hidden 条目 40400；
  管理端输出与后端 `_news_out` 同构（images/cover/videoUrl/playCount/variant/publishedAt/
  hotScore/hidden 三件套）。
- **踩坑（mock 路由分段）**：`/admin/news/:id/hide` 切分后 `id` 是 `b`、动作是 `c`，
  初版写成 `b === 'hide'` 恒不命中——分段路由的段位先数清楚再写断言。
- **踩坑（契约脚本置顶用例与种子状态耦合）**：初版「置顶」PATCH 打在演示条 n3 上，
  而 n3 种子即 `isTop:true`，首次 PATCH **无变化不留痕**，与「两次变化记 2 条」的断言冲突。
  改为 **flip-flip**：记录初值 → 先 PATCH 翻反值（顺带验证蛇形 `is_top` 被忽略）→
  再 PATCH 翻回——**与初始状态无关**，两次变化必然产生。收尾自动恢复演示条不污染库。
