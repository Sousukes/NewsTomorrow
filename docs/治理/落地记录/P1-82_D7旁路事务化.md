## 批次 P1-82（D7-a）：旁路写入事务化 —— 兑现「不做 outbox」后的真修复

D7 的结论是**不做 outbox**（前提不成立：所有旁路都在同一个库内，见
`docs/后端/D7领域事件outbox评估.md`）。本批把评估里指出的三处「两次 commit」修掉。

## 交付

| 位置 | 改动 |
| --- | --- |
| `app/routers/comments.py::create_comment` | 通知移入主事务（与评论、冗余计数同一次 commit） |
| `app/routers/comments.py::set_like` | 同上（点赞 + 点赞通知同一次提交） |
| `app/reports.py::create_report` | 阈值判定与 `_auto_hide` 并入主事务（`flush` 后判定、单次 `commit`） |
| `app/ranking.py::bump_hot_score` | 失败不再只写日志，改为**落审计** `side_effect.failed` |
| `app/routers/admin/_shared.py` | 新增审计动作常量 `AUDIT_SIDE_EFFECT_FAILED` |
| `tests/test_side_effects.py`（新） | 8 项：通知同事务、点赞同事务、热度失败落审计、**两条原子性用例** |

## 修的是什么

| 位置 | 旧行为 | 后果 |
| --- | --- | --- |
| 评论 / 点赞 | 评论 commit → 通知再 commit（try/except 兜住） | 评论成功、通知**永久丢失**，只留一条 warning 日志 |
| 举报 | 写举报 commit → 达阈值再 `_auto_hide` + commit | 举报成功、**处置没生效**；且阈值只在提交新举报时检查，**没有自愈路径** |

热度（`bump_hot_score`）继续 best-effort（派生数据、可由定时任务重算），
但失败改为落审计——日志在容器里没人看，等于静默失效。

## 测试里最有价值的一条：假绿与反向变异

「通知与评论同事务」开始时是**假绿**的：我写了断言评论与通知都存在，
但在通知**成功**的路径下，「两次提交」的旧写法同样能满足它——
两种写法在成功路径上的最终状态一模一样。用反向变异一验就露了：
把代码改回两次提交，**测试全过**。

于是补了真正能区分的用例：**让通知失败**，看评论是否跟着回滚。
- 同事务 → 评论不落库、接口 5xx；
- 两次提交 → 评论留下、通知丢失。

补测之前还抓到自己一个低级错误：评论那条原子性用例忘了 `_seed_news`，
请求在 404 就返回了，根本走不到通知——**那条用例在两种写法下都会过**。

最终反向验证（把代码改回两次提交）：

```
FAILED test_side_effects.py::test_comment_rolls_back_when_notify_fails
FAILED test_side_effects.py::test_like_rolls_back_when_notify_fails
2 failed, 6 passed      ← 变异被抓到
还原后：8 passed
```

## 行为变化（对使用者可见）

- 评论 / 点赞：若通知写入失败，整个请求失败（不再「评论成功但收不到通知」）。
  这是有意取舍：同库同级的两个写入不该不同生共死。
- 举报：达阈值时举报与处置同成同败（外部响应 `autoHidden` 语义不变）。
- 契约未变：接口路径、请求/响应结构、错误码都不动。
