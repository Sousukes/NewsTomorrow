## 批次 P1-15（2026-10-15）：运营审计日志（谁改了什么）
- **背景**：P1-14 的权限体系回答了「谁能进后台」，但没回答「谁干了什么」——源被停用、
  换地址、删除，管理员被加入或移除，**此前全部无痕迹**；多个管理员共用后台时，
  事后排查只能靠猜。用户选了这批（另两个候选是源超时告警、源级限流）。
- **埋点范围**：源 增 / 改 / 删 / 重置、管理员 增 / 删；动作用 `对象.动作` 命名
  （`source.update` 等），前端据此映射中文标签，不必再维护一份枚举表。
- **只记真正变化的字段**：前端 PATCH 常因表单整体提交而带上未变字段，全量记录会灌满
  时间线。故更新只写 `changes`（旧→新）diff，且 **无变化时完全不留痕**（有测试守着）。
- **快照必须在删除前取**：删完行就没了，事后无从知道删掉的是什么。
- **同事务写入**：`record_audit()` 不提交，由调用方与业务变更一起 commit——
  「改成功了但没留痕」比「改失败」更糟，所以刻意不做 try/except 静默降级。
- **游标用自增 id 而非时间戳**：`created_at` 是秒级精度，同秒多条会让 keyset 比较
  出现重复/遗漏（评论分页踩过同一个坑，这次直接绕开）。
- **前端**：新增 `/admin/audit` 时间线（中文动作 / 对象 / 操作者 / 时间 / 字段级变更，
  `enabled` 翻成「启用→停用」而非 true→false）；游标分页「加载更多」；
  **源管理页每行加「历史」**直达该源（`?target=`），管理员页加审计入口。
- **mock 后端同步**：进程内审计数组 + 三端点埋点 + `/admin/audit`（含游标与 target 过滤、
  非法游标 40003），`dev:api` 可完整体验。
- **踩坑**：
  1. **编辑冲突导致埋点重复**——先后两次 Edit 都以 `db.delete(row); db.commit()` 为锚点，
     把 `record_audit` 在「移除管理员」里插了两次，表现为一次移除产生两条审计。
     是 `test_admin_add_and_remove_recorded` 断言 `["admin.remove","admin.add"]` 逼出来的
     （长度不对，而非内容不对）。**改同一函数时，第二次编辑的锚点要包含第一次新增的行**。
  2. 同类问题也出现在测试文件：给 `test_migrations.py` 插入新用例时，old_string 吞掉了
     下一个函数的 `def` 行——插入后必须读回上下文确认结构完整。
- **测试**：后端 270 → **284 项**（新建 `tests/test_audit.py` 13 项 + `test_migrations` 1 项）；
  前端 214 → **221 项**（`views/AdminAudit.spec.ts` 7 项）；
  契约 `CHECK_ADMIN=1` 65 → **72 项**（mock 与真实后端 PG 各跑一遍均 72/72）。
