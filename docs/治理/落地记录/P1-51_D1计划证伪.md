## 实验跑了什么

本地没有 PG 守护进程，所以只覆盖 SQLite——而 SQLite 恰是 ALTER 更难的一端：
没有原生时间类型，改列要整表重建。用真实 `batch_alter_table` 回答四问。

## 三个结论

1. **存量列混着五种值**：ISO+offset、naive、`''`、`NULL`、展示文案「刚刚」；
2. **决定性的一条**：**空串与展示文案会让整表重建直接失败**——不是"变成 NULL"，
   是迁移报错。意味着**任何 D1 方案都必须先做数据清洗**，而原计划里没有这一步；
3. 干净数据上，转换后 `ORDER BY at DESC` 仍等价于时间序，`NULL` 原样保留。

## D1-a 为什么被否掉

逐列核实"哪些列只排序、不参与 SQL 侧比较"，答案是**几乎不存在**：

| 列 | 实际用途 |
| --- | --- |
| `news.published_at` | 抓取保留期清理 `published_at < cutoff` |
| `comments.created_at` | 管理端 **keyset 游标**比较 |
| `news.hot_score_at` | 热度衰减筛选 `< cutoff` |
| `hit_logs.*.created_at` | 命中日志保留期清理 |

剩下的只写入列（11 处写入点）收益只有"类型诚实"，代价却是 11 处改造
+ 引入**第二套写入口径**（`now_dt()` 与 `now_str()` 并存，正是 A3 刚消除的漂移）
+ 一次不可逆的双方言迁移。**收益不足以抵消它引入的新漂移面。**

## 修正后的顺序

1. **D1-0（先做）**：数据清洗——`''` 归一为 `NULL`、清理误入的展示文案。
   这一步与列类型无关，做完就消掉了 `coalesce(x, '')` 的必要性（换 `NULLS LAST`），
   顺带修掉一个既有的正确性隐患（空串参与排序/过滤的语义歧义）；
2. **D1-1**：再改参与 SQL 侧比较的列，cutoff 一律**参数绑定**；
3. 展示型三列不进任何一批——它们不是时间。
