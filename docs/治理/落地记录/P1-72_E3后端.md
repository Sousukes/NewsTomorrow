## 六个实现要点

1. **`rank_key` 把衰减乘在整体外面**：`(hot_score + 频道加分) × 衰减`，而不是从加分里扣。
   扣加分只削弱偏好增益；乘整体才把该来源的**全部竞争力**按比例压下来，这才是
   "少来点"的预期效果。空集合时系数恒 1，与无负反馈完全一致。
2. **游标键必须复算整串表达式**（本批实测踩到）：SQL 侧是整体相乘，Python 侧只给
   "加分"乘衰减时，在**用户没有任何频道偏好**（加分为 0）的场合必然分叉——
   游标存 55、SQL 比 16.5，续页把翻过去的内容又翻回来且**永不终止**。
   `test_paging_consistent_with_stable_feedback` 就是抓这个的。
3. **单条负反馈对所有排序生效**（含 latest）：它是用户的明确表达，
   "点过不感兴趣的那条又出现在最新里"比少一条更难解释。
4. **曝光去重只作用 for-you**，latest/hot 保持完整——时间流过滤会漏内容。
5. **探底保护**：已曝光占可见内容 > 60% 时当次放弃去重并回传 `dedupRelaxed`。
   否则小库/重度用户会拿到空页，那正是「关注流」踩过的坑（E6b）。
6. **互斥校验放在路由而不是 pydantic**：互斥是域规则，该回 42207；
   塞进 `model_validator` 会被统一处理器收敛成 42200，调用方分不出
   "字段写错"与"意图不明"。

## 一处对设计的偏离（有依据）

设计原文说互斥"放在 model_validator 里"，实现时改为路由内校验，理由如上（第 6 条）。
另：单条负反馈的范围从设计中的"作用于 for-you"扩大为**所有排序**——设计 §九 的验收
标准写的正是"刷新后不回来"，两者取更严格的那个。

## 契约断言的两处修正（提交前回归抓出）

1. **「latest 仍保留该内容」原本是巧合通过**。它断言"for-you 的第一条
   出现在 latest 的前 50 名里"——但 for-you 按热度排、latest 按时间排，
   两者没有这种关系，头条完全可能落在 latest 的第 50 名之后。首跑就红了。
   改为**对比同一份 latest 列表在曝光上报前后是否逐条一致**（基线在上报之前取）：
   这才真正表达"曝光去重只作用 for-you、时间流不受影响"。
2. **两条曝光断言原本是空转的**。它们只判"抛错就算通过"，而 `token` 缺失时
   同样抛错（401）——漏传 `DEMO_PASSWORD` 时正是靠这条蒙过去的。
   改为断言双端文案都含 `ids`，把"校验拒绝"和"鉴权失败"区分开。

> 另：`catch {}` 吞掉 40304 是本项目反复踩的坑（记忆 #7 / #39）。本批首跑
> 就是因为漏传 `DEMO_PASSWORD`、而断言又判得太松，才出现"看着像功能有问题"。

## 顺带修正：自己引入的分叉

第一版 `_boost_of` 只把衰减乘到"频道加分"上，与 SQL 的整体相乘不一致。
该 bug 在**无频道偏好的用户**身上必然触发（加分恒 0 → Python 侧无衰减、SQL 侧有），
且症状是翻页循环而非报错——已改为复算整串表达式并写入注释，防止回退。
