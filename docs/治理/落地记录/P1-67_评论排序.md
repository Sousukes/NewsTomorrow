## 批次 P1-67（E6 前半）：评论排序「最新 / 最热」

E6 原立项为「评论排序 + 关注作者」（成本 S）。开工后发现两者不是一个量级：
**关注作者缺实体**——本项目没有作者表，`news.source` 只是媒体名字符串，
要做关注得先有「作者/来源」的身份与关注流（否则关注按钮没有任何消费方，是死功能）。
故本批只做**评论排序**（自包含、可完整验收），关注作者拆为 E6b 另立批次。

## 四个技术要点

1. **游标必须携带 sort**：`latest` 与 `hot` 的排序键不同（时间 vs 点赞数）。
   若游标只存 id，用 `hot` 的游标去续 `latest` 会静默错位——拿到一页
   「看起来正常但缺几条」的数据。这是 news 列表在 P1-7 踩过的同一个坑，
   这里直接复用处方：`[2, sort, likes, created_at, id]`。
   **排序不一致时游标作废、从头取第一页**（而不是报错或错位续接）。
   旧格式（裸 id）仍按 latest 兼容——它只可能由 latest 产生。

2. **`likes` 的 NULL 必须当 0**：`likes` 允许为空（历史行）。直接写
   `Comment.likes < x` 会把 NULL 行整行排除，表现为「翻到第二页，零赞评论凭空消失」。
   排序与 keyset 条件统一走 `coalesce(likes, 0)`。

3. **失败要回退排序**：`setSort` 失败时把 `sortByArticle` 还原并返回 false。
   只换高亮不换内容（或反之）都是撒谎——界面上的激活态必须与列表真实顺序一致。
   视图侧据此回退标签并提示「切换排序失败」。

4. **切换排序清空展开态**：列表被整体替换，旧的「查看全部回复」展开与回复目标
   都失去语境（回复对象可能已不在列表里）。

## 刻意的不做

- **回复不参与排序**：讨论先后是回复唯一合理的顺序，按赞排会把一段对话打散。
- **mock 不做真游标**：一次返回全部主评论（既有行为）。`sort=hot` 按点赞数排序，
  但 mock 没有 `created_at`，同赞时只能用写入序号近似——**这是 mock 的诚实边界**。
- **hot 的分页天然不稳定**：分页途中某条评论被点赞就会跨过游标位置，可能重复或漏一条。
  当前 UI 一次取完列表（主评论不分页），无实际影响；已在模块 docstring 写明。
