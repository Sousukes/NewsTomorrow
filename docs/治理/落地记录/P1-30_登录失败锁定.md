## 批次 P1-30（2026-10-18）：登录失败锁定（C2）
登录限流此前只按 IP（`login:<ip>`，10 次/分）。它防得住「一个 IP 猛刷」，
防不住「换 IP 打同一个账号」——分布式爆破的每个 IP 都是首次访问，IP 维度
干干净净，而受害账号被无限试密码。账号维度的失败计数补这一面。

- **新模块 `app/login_guard.py`**：账号维度失败计数 + 临时锁定，键为手机号
  （与 IP 无关），与 IP 限流同款双实现（进程内 / Redis 共享）。
- **判定流程**：格式校验 → 锁定预检 → 查库 + 验密。四个防绕过设计：
  - **预检 `blocked()` 只窥探不计次**（限流器新增方法）：否则被锁期间的
    继续尝试会给计数器 +1，锁定期被攻击者自己的请求无限续期；
  - **锁定先于验密**：已锁账号连 pbkdf2 都不算，成本趋零；
  - **不存在的账号同样计数**：锁定先于用户查询，响应只有 42902 / 40101
    两种——若只锁已存在账号，「同号有时 429 有时 401」就是账号枚举 oracle；
  - **成功登录 `reset()` 清零**：计数只反映「连续」失败，5 次手滑 + 1 次
    成功 + 1 次手滑不该锁。
- **配置**：`LOGIN_FAIL_LIMIT`（默认 5）/ `LOGIN_FAIL_WINDOW_SECONDS`
  （默认 900）。阈值给到 5 是权衡：账号锁定的固有误伤是「持正确密码的
  用户可能被故意锁一个窗口」，再低就连累真人；窗口 15 分钟是「等一会」。
- **契约**：429 + 新错误码 **42902** + `Retry-After` 头。异常处理器补透传
  `exc.headers`——此前会把它重新拼装的 JSONResponse 丢掉，429 只剩一句
  「请稍后再试」，客户端无法合理安排重试。
- **跟随 `RATE_LIMIT_ENABLED` 总开关**：与 IP 限流同一个开关，测试环境
  （conftest 钉 false）不受失败计数影响。
- **无迁移**：计数走限流器（内存 / Redis），不落库——每次失败写一行 users
  是给爆破攻击送弹药（写放大）。
- **回归**：后端 pytest 618 → **626 全绿**（`test_login_guard.py` 6 项 +
  `test_units.py` 限流器 `blocked`/`reset` +2 项）；契约双端不受影响
  （每轮只做 1 次失败登录即成功，成功清零）；前端零改动（42902 走通用
  错误展示路径，message 即文案）。
- **文档**：后端 README（限流节整段 + 错误码 42902 + 测试计数 + 新测试
  文件条目）、`.env.example`（两个新变量）、速查表（汇总表 P1-30 行 +
  详情节）、本记录。审查报告中 C2 已标注为已处置。
