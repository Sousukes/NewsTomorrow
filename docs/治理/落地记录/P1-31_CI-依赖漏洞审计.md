## 批次 P1-31（2026-10-18）：CI 依赖漏洞审计（C8）
此前的 CI 只验「代码能跑」，不验「依赖有没有已知漏洞」——一个 high 级
CVE 可以在全绿的状态下潜伏到被利用。本批给两个 job 各加一道闸门。

- **前端**：`npm ci` 之后跑 `npm audit --audit-level=high`（放在类型
  检查之前，fail fast 在便宜的地方）。
- **后端**：装完依赖后跑 `pip-audit`。
- **两个「不这么做就会天天红」的细节**：
  - `pip-audit` 审计的是**整个已安装环境**，venv 自带的 pip 也在范围内。
    旧版 pip 自身就有通告（PYSEC-2026-3721，26.2 修复）——所以步骤里先
    `pip install --upgrade pip`。审计闸门最怕「狼来了」：红几次之后团队
    对红色就没信任了，真漏洞也被一起忽略；
  - `npm audit` 走官方 registry 的审计端点，而开发常用的 npmmirror
    **不实现** `/-/npm/v1/security/*`（报 NOT_IMPLEMENTED）——本地自查
    要临时 `--registry=https://registry.npmjs.org`，CI 用默认 registry
    没有这个问题。这是镜像能力缺口，不是配置错误。
- **阈值取 high 的理由**：低危/中危的修复主动权常在间接依赖上游，拦在
  CI 里只会制造无力修复的红色；高危及以上才具备「不修不能上线」的性质，
  其余交给 dependabot / 人工评估。
- **本地复验（CI 改动的唯一可信验证方式）**：按 CI 同款命令链在干净
  venv（只装 requirements.txt，排除本机其他会话的污染包——第一轮就
  被 chromadb 骗了一下）复跑：Python 零发现、npm 0 漏洞。当前依赖面
  干净，闸门上线不会立刻红。
- **无代码 / 契约 / 迁移变更**，纯 CI 配置。
- **文档**：后端 README（迁移章节 CI 注释块补 C8 说明）、前端 README
  （CI 条目 + 依赖审计说明）、速查表（汇总表 P1-31 行 + 详情节）、本记录。
  审查报告中 C8 已标注为已处置。
