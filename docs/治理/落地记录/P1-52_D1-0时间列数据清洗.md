## 批次 P1-52（2026-10-18）：D1-0 时间列数据清洗（迁移 0029）

P1-51 证伪了 D1-a，并把修正后的第一步定为 **D1-0**：把时间列里
"空串哨兵"归一为 `NULL`。这是**本项目第一次有行为风险的迁移**，所以本批的重点
不是"改数据"，而是**证明改数据没有改变行为**。

## 为什么可以安全地做

动手前核对了**所有读点**，结论是清洗**行为等价**：

| 读点 | 写法 | 清洗后 |
| --- | --- | --- |
| 抓取保留期清理 | `or_(published_at.is_(None), published_at == "")` | 已同时兼容两者 |
| 列表排序 | `coalesce(published_at, '')` | NULL 仍归一成 `''`，沉底不变 |
| 热度衰减 | `ranking._parse_dt(None)` → 未知分支 | 与空串同一分支 |

也就是说，**代码早就在同时兼容两种表达**（作者当年写 `or_(... == "")` 时，
就知道空串会出现）。所以本迁移**不改任何查询代码**——
那行 `== ""` 是防御性检查，删掉反而会让未迁移的库把 `''` 当成"有发布时间"。

写入侧也早已不产生空串（`published_at` 只写 `None` 或 `.isoformat()`），
所以清洗的是**历史存量**，新数据不会再进来。

## 迁移 0029 做了什么

- 白名单复用 0027 的表/列清单，**只含绝对时间戳列**；
- **刻意排除** `news.time` / `comments.time` / `messages.time`——
  那里 `''` 是合法默认值，归一成 NULL 会让展示层多出一堆"空时间"；
- `''` → NULL；
- **不可解析的脏值（如「刚刚」）不清洗、不编造**，只计数打印——
  与 0027 同一立场：留一条可查的脏数据，比静默改掉更诚实；
- **downgrade 空操作**：`''` 与 NULL 语义等价但技术上不可区分，
  强行回退等于把"正确"改成"错误"。

## 三种验证

1. **等价性测试**（7 项）：造 ISO / `''` / NULL 三种行，断言清洗前后
   **列表可见集合**、**排序位置**、**热度衰减分支**三者一致；
2. **真实迁移链路**：`alembic downgrade 0028` → 注入脏数据 →
   `upgrade head` → 断言 `''` 变 NULL、真值未动、**展示列的合法空串未被误清洗**；
3. **写库护栏**：`published_at` 不允许写 `''`（将来有人写了当场红，
   而不是等下一次迁移失败才发现）。

另有两项护栏是读**模块的 `_TABLES`** 而不是搜源码——0029 的文档字符串里
就写着 `news.time`（说明为什么排除它），按子串判断必然误报。
