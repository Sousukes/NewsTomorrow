## 批次 P1-26（2026-10-17）：搜索分页语义（A5）+ 回复预览下推（B1）
审查清单里两个**成本 S 但收益直接可见**的项，合并为一个批次。

- **A5 · 搜索「加载更多」整段替换**（`views/SearchResults.vue`）：
  `runSearch` 里 `results.value = res.list` 对每一页都成立，于是点「加载更多」
  只会把列表换成第 2 页——用户永远看不到第 1 页，而按钮还写着
  `加载更多（2/5）`。改为：第 1 页替换、后续页**追加并按 id 去重**
  （翻页之间若有新增/排序变动，同一条可能出现在两页）。
- **A5 的第二个坑（终止条件）**：原判断是 `results.length >= total`。`total` 是
  offset 分页的 `COUNT` 估算，与**去重后的本地长度不是同一个量**：去重后
  `length` 会小于 `total`，按钮就一直显示却点出来空；服务端 `total` 偏小时
  又会提前消失。改用服务端 **`hasMore`**——它就是「还有没有下一页」的定义。
- **B1 · 回复预览把 LIMIT 下推到 SQL**（`routers/comments.py::_decorate_roots`）：
  原实现在同一个 SELECT 里算 `row_number()`，但 **SQL 不允许 `WHERE` 引用窗口列**，
  只能在 Python 侧 `if rn <= 2` 截断——等于把每个主评论的**全部回复**捞进内存，
  爆款评论（数百上千条回复）× 一页 20 条主评论就是 20 份全量回复，
  这是评论页最陡的性能悬崖。改为**子查询内算 `rn` + 外层 `WHERE rn <= 2`**，
  ORM 侧用 `aliased(Comment, subquery)` 把子查询列映射回实体。
- **B1 的连带风险（已加回归）**：过滤条件（`is_deleted` / `hidden`）必须写在
  **子查询内部**——下推时漏掉，预览就会露出不该可见的内容。
- **测试**：后端 591 → **594**（`TestCommentReplies` 9 → 12 项：`rn <= N` 必须出现在
  **实际执行的 SQL** 里——用 `before_cursor_execute` 捕获语句断言，回退成 Python
  侧截断即失败；30 条回复时预览仍是最早 2 条且 `replyCount` 计全部；预览跳过
  已删除与已隐藏）。前端 469 → **474**（新增 `views/SearchResults.spec.ts` 5 项，
  该视图此前**没有测试**——11 个用户侧视图无 spec 的分布倒挂问题由此开始收敛）。
- **踩坑（性能修复要有能失败的断言）**：性能优化的回归测试最容易出现「改完了
  测试还是全绿，因为测的是行为不是性质」。下推到 SQL 这件事**不改变任何可见行为**，
  所以除了行为断言（最早 2 条、计数正确、跳过已删已隐藏），必须再加一条
  **结构性断言**：捕获真实执行的 SQL，断言 `rn <=` 出现在语句里。
  否则下次有人把过滤搬回 Python 侧，全套测试依然全绿。
- **踩坑（vue-router 的 route 必须 mock 成响应式）**：新写的视图 spec 里
  `useRoute: () => ({ query: routeQuery })` 若 `routeQuery` 是普通对象，改它的
  `q` **不会触发 watcher**（没有响应式依赖），「换关键词回到第一页」这条用例会
  失败于「调用参数仍是旧关键词」。必须用 `reactive()` 包一层——真实 vue-router
  的 route 本来就是响应式的，mock 要对齐这个性质。
