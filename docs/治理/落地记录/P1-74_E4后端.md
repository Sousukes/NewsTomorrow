## 五个实现要点

1. **判据分两档，从便宜到贵**：先比**归一化标题相等**（NFKC + casefold + 去
   P/Z/S/C 类字符，方言无关），再在 PG + pg_trgm 可用时比
   `similarity() >= 0.9`。第一档让 SQLite 环境不至于退化成"几乎没用"——
   "标题！" vs "标题"在三元组下只有 0.4，却明显是同一篇。
2. **阈值 0.9 有实测依据，不是拍的**：真实库里要合并的目标相似度全是 1.000，
   而同源「广州队不敌天津队 / 不敌山东队」是 **0.652** 且是**两场不同的比赛**；
   源自己改标题重发落在 0.65~0.80，**刻意不合并**——那是源的行为，留给运营
   判断更安全。测试把这两组真实标题写进断言（含 `0.652` 的口径对齐），
   阈值一旦被改动会立刻可见。
3. **只在新增分支判重**：按 id 命中的行走更新路径，不受影响；同一条被再抓到
   计 `updated` 而**不计** `deduped`——两者在日志里分开，才看得出"入库 N 条"
   里有没有混着重复。
4. **批量内自判重**：同一批里两条互为近邻时，第二条还没落库，查库查不到。
   用一个 `handled` 字典在本批内记账，否则同一批里照样插两条。
5. **命中后保留旧行**：id 不变、`comment_count` / `play_count` 不丢，只增量刷新
   标题 / 摘要 / 正文 / 图片 / 时间。互动数据跟着一条被删掉的重复行一起消失，
   是最难被察觉的一种丢数据。

## 存量清理脚本的安全边界

`prune_duplicate_news.py` 处理**历史** 3 组重复（设计与实现刻意分成两件事：
"以后不再产生"风险低，"改历史"风险高得多）。默认只报告，`--apply` 才删：

- 只按**归一化标题**在同一来源内分组，不做相似度聚类（跨源已证伪）；
- 每组保留互动量最高的一条，并列取发布时间最新的（与 `find_duplicate` 排序口径
  一致，"入库时保留哪条"和"清理时保留哪条"不互相矛盾）；
- 有**依赖行**（评论/收藏/浏览历史/消息）或**互动计数**的行不删，只报告；
- 隐藏行不参与分组（与 `find_duplicate` 同口径）。

已在真实 PG 库上跑过只读模式：3 组 / 6 条，可删 3 条、跳过 0 条、6 条均无任何
依赖。**未执行 `--apply`**——删真实数据需人工确认，脚本与结论一并交给你决定。

## 顺带修掉两个提交前回归才暴露的真缺陷

提交前跑契约检查（真实 PG）时暴露的，都与 E4-a 无关，但都在关键路径上：

### 1. `/admin/sources/{key}/health` 在 PG 上一直返回 500（P1-53 遗留）

根因：P1-53（迁移 0030）把 `rss_source_health_events.at` 迁成 `DateTime`，
但 `feeds/health.py::daily_points` 仍在做 `substr(at, 1, 10)` 按天分桶——
PG 上 `substr(timestamptz, …)` 直接报"函数不存在"。

**为什么一路没被发现**：SQLite 的 `substr` 对文本可用，而单元测试跑在 SQLite；
这条路径只有契约检查（真实 PG）能碰到。也就是说，**P1-53 之后的所有 PG 环境里
这个管理端端点一直是 500**。

修法：分桶改到 Python 侧，读回一律经 `iso_utc()`（与同文件 `window_summary`
同一处方）。**没有**改用 `date(at)` 这类数据库日期函数——PG 的
`date(timestamptz)` 按**会话时区**截断（本地实测 PG 是 +08），SQLite 按文本
解析，两边会把跨 UTC 午夜的事件分到不同的一天，那正是当初引入 `substr`
想避免的"两种方言行为不一"。

回归护栏：`test_health_history.py::TestDailyPointsOnPostgres` 直接连 PG 跑
（`TEST_PG_URL` 未配置或连不上则 skip，CI 的 postgres service 已在同一 job 内），
并已**反向验证**——把实现换回 `substr` 后该用例以完全相同的报错失败。
同时锁住"按 UTC 分桶"的语义（造一对同 UTC 日、不同本地日的事件）。

### 2. 契约脚本的联想探针会被历史运行挤出前十

根因：探针词所有运行共用「联想探针」前缀，dev 库的 `search_logs` 逐次累积，
而 hot 源按「次数倒序 + 词典序」取前 N 条——实测累积到 10 个旧探针后，
当次探针必然落榜，断言变成"看库有多脏"而不是"看联想好不好用"。
修法：前缀改为每次运行唯一（`探<时间戳后6位>`）。

> 这两条加上契约检查本身，构成本批真正的"提交前回归"价值：
> 全量 pytest（SQLite）对第 1 条是全绿的，契约检查（PG）才把它揪出来。
