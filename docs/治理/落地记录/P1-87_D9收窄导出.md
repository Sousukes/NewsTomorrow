## 批次 P1-87（D9）：收窄无消费者的导出，并把扫描固化成脚本

## 背景

D9 是 P1-85 清点时上账的 S 级债：3 个仅本文件内使用却 `export` 的函数。
收窄它们本身是十分钟的活，但**没有护栏**——有人再加一个无消费者的导出，
仍然没人发现，几年后又是一轮清点。所以本批做两件事：修掉，以及让"发现"可重复。

## 一、修掉的导出（实际是 6 个，比账上记的多）

账上记的是 3 个（`api/http.ts` 的 `clearStepUpToken` / `requestStepUp`，
`api/follows.ts` 的 `mockSourceDirectory`）。写扫描脚本时**又捞出 3 个**：
`src/utils/contrast.ts` 的 `parseHex` / `relativeLuminance` / `meetsAA`。

原因：P1-85 那次清点用的是一次性脚本，输出被 `head -25` 截断，
43 项里只看到前 25 项——**截断让清点本身漏了项**。

| 符号 | 处置 | 依据 |
| --- | --- | --- |
| `clearStepUpToken` / `requestStepUp` | 改为模块内可见 | 唯一调用点都在 `http.ts`；"要不要弹二次校验"是传输层职责，业务代码不该自己决定 |
| `mockSourceDirectory` | 改为模块内可见 | 只服务 `follows.ts` 的离线分支，是 mock 实现的内部件 |
| `parseHex` / `relativeLuminance` | 改为模块内可见 | `contrastRatio` 的内部步骤 |
| `meetsAA` | **删除** | 全仓零引用（连定义行之外都没有）；三行的便捷包装，需要时加回来即可 |

每一处都补了"为什么不导出"的注释——**只写结论不写理由，下一个接手的人会把它加回去**。

## 二、把扫描固化成 `scripts/check-dead-exports.mjs`

P1-85 的清点脚本是一次性的（跑完就删），所以同样的活儿下次还要重做。
本次固化为正式脚本：

- 判据：「本文件之外零引用」。测试与 story **不算消费方**（它们引用符号是为了测它）；
- **函数类死导出 → 计入失败（exit 1）**：这类几乎一定是该收窄的；
- **类型类只报告、不计失败**：`interface` / `type` 常常是"给未来消费者"或与同文件
  实现配套，误报率高于函数类（当前 37 个），交给人工判断；
- 脚本头写清了它**看不到动态引用**（字符串拼出来的调用、`:is` 动态组件），
  命中项要人工确认再删——**脚本是放大器，不是判决书**。

反向变异验证：往 `contrast.ts` 里加一个无消费者的导出 → exit 1 并精确指出位置
（`utils/contrast.ts: __mutationDeadExport（本文件自引用 0 次）`）。

> 顺带说明：类型类那 37 个**刻意不动**。它们多数是 api 层的响应信封类型
> （`NewsPage` / `CommentPage` / `LoginParams`…），删或不删都不影响行为，
> 而逐个判断"是不是给未来留的"需要读设计意图——那是另一批的活，
> 不该塞进一个"收窄导出面"的小批次里把水搅浑。

## 四、一个流程教训
