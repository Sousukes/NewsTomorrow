## 批次 P1-18（2026-10-15）：失败分级与熔断（404 不该和超时同等重试）
- **背景**：P1-17 把「N 个源同时挂」的**消息噪音**压成了一条，但它没解决更前置的一个问题
  ——**所有失败在此前被当成同一件事处理**。404 和超时被同等重试、同等计数、同等告警，
  于是真正该做的两件不同的事（"等它自己恢复" 与 "去改配置"）都被含糊成了"再试一次"。
  源多了以后这不是洁癖问题：对一批 404 的源反复重试，是在给对方站点的错误日志刷流量。
- **设计①：先分级，再谈重试**（`fetcher.FetchError.kind`）。
  - `transient` 可重试：超时 / 连接重置 / 5xx / **429**（对方只是限流，等一会儿就能过）；
  - `permanent` 永久：其余 4xx（401/403/404…）/ robots 拒绝 / **解析成功但 0 条**
    （拿不到条目的地址不会自己变好）。
  - **`kind` 必须作为结构化数据穿过线程池**：异常被 `str(e)` 拍平后就没法再分类了，
    而用元组返回会在半路丢掉它——所以它挂在 `FetchError` 上，一路带到
    `record_fetch_result`，最终存进 `rss_sources.failure_kind`。
- **设计②：只有可重试的才重试**。此前对 404 也重试 3 次，纯属浪费。
  `_fetch_with_retry` 遇到非 `transient` 立即跳出，不消耗剩余次数。
- **设计③：计数落库**（`consecutive_failures`）而非进程内变量——
  后者多实例之间不共享、重启即清零，熔断阈值就永远判不准。成功一次即归零。
- **设计④：熔断**（`FEED_CIRCUIT_THRESHOLD`，默认 5）。连续失败达阈值后写
  `next_retry_at`，**冷却期内整轮跳过该源**，到期自动恢复尝试，不需要人工干预。
  与「礼仪跳过」同一条规则：**被跳过的源本轮不刷新健康状态**，
  否则"多久没成功"永远归零，告警永远不会响。
  > 熔断的意义是"别再给一个正在故障的站点送请求"，**不是"这个源不要了"**。
  > 所以它自愈、也不改 `enabled`——改 `enabled` 是运营决策，不能由抓取器代劳。
- **设计⑤：自动禁用默认关闭**（`FEED_AUTO_DISABLE_PERMANENT=0`）。
  连续**永久**失败达阈值时可自动置 `enabled=False`，但**默认永不触发**：
  一个源 404 一周就被静默关掉、且没人记得重新打开，**比一直重试更糟**。
  "自动禁用"必须由运维主动选择。开启后**每次触发都写审计**（`source.auto_disable`，
  `actor_phone="system"`，detail 带连续次数与最后错误）——
  「谁把这个源关了」事后查不到，是最难排查的一类问题，**留痕是这项功能的准入条件**。
- **设计⑥：告警带上性质**。P1-17 的原因分组从 3 类扩到 5 类，且单源原因也区分对待。
  打印出来逐个读过（教训见 P1-17——断言测不出"读起来像不像人话"）：

  ```
  [断网：12 源全超时] 临时失败 12 条（新浪科技、cnBeta、虎嗅、36氪、InfoQ 等）
  [源地址集体失效]   永久失败 4 条（旧源A、旧源B、旧源C、旧源D）
  [混合]             永久失败 2 条（死源A、死源B）；临时失败 3 条（新浪科技、cnBeta、虎嗅）

  连续 7 次失败：HTTP 404（永久性，需人工处理）
  连续 3 次失败：ReadTimeout: 读取超时（可重试，系统会自动继续尝试）
  最近一次抓取失败：HTTP 503（可重试，系统会自动继续尝试）
  连续 2 次失败：解析后无条目          ← 老数据无 failure_kind 时退化，不猜
  ```
- **前端表达**：源列表按性质分色——「连续 N 次失败 · 永久性」标红（等不会好，得去改配置）、
  「· 可重试」用中性样式；冷却期内显示「冷却至 xx:xx」（不显示的话，运营看到
  抓取时间停住会以为定时任务挂了）。**只失败一次且无性质时不出标签**——
  偶发抖动多显示一格就是噪音。审计页 `source.auto_disable` 的 `system`
  渲染成「系统自动执行」而不是一个假账号。
