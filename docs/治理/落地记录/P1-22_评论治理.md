## 批次 P1-22（2026-10-15）：评论治理（先隐藏，再核实）
- **背景**：评论是 UGC 里风险最高的一类——广告、辱骂、剧透、未核实传闻。此前只有
  软删除一条路（`DELETE /news/:id/comments/:cid`，作者侧、不可逆）：删了上下文全丢、
  作者看不到「为什么没了」、运营也不愿轻易动手。**缺一个「先隐藏再核实」的中间态，
  评论风险的暴露时间就没有上限**（与 P1-20 资讯下架同一处方，只是处置对象从资讯换成评论）。
- **设计①：软隐藏非硬删，与 is_deleted 分工**。`comments` +3 列（迁移 **0022**：
  `hidden` 非空 `server_default=false` / `hidden_at` / `hidden_reason`）。
  `is_deleted` = 作者侧软删除（**不可恢复**），`hidden` = 运营治理（**可恢复**），
  两条正交、查询条件互不干扰——把两种「看不见」混进一个字段，事后无法解释是谁造成的。
- **设计②：理由必填**。schema 层 `Field(min_length=1, max_length=300)` + 非空白校验，
  空 / 纯空白 / 超长一律 **42200**；前端另行拦截（空理由弹窗不关、不发请求）。
  **「留痕是准入条件」**——没有理由的隐藏，在申诉与复盘时不可辩护。
- **设计③：公开五路实时过滤**。主列表 / 回复列表 / 评论计数 / 点赞 / 回复创建五路
  全部即时生效（**后审核模式**：不动内容管线，恢复即实时可见，无需等任何定时任务）。
  **主评论隐藏后其回复亦不可见**——回复失去语境，裸露出来只会让人困惑。
- **设计④：双码分离**。公开端「已隐藏」与「不存在」**同为 40401**（不对外泄露
  「曾被隐藏」）；管理端 **40405** 区分，方便排障。与 P1-20 的 40400 / 40404 同一构思。
- **设计⑤：计数联动 + was_visible 守卫**。隐藏使 `news.comment_count` −1（下限 0）、
  恢复 +1——「显示 N 条却只看到 N−1 条」是 P1-12 修过的旧 bug。守卫只在**原本可见**
  时才扣减，重复隐藏不会把计数扣成负数。
- **设计⑥：幂等**。重复隐藏**不覆盖原理由、不重复记审计**（第二次直接返回当前状态）；
  恢复清空 `hidden_at` / `hidden_reason`——留着会让下一次隐藏的审计读起来张冠李戴。
- **设计⑦：不建索引**。`hidden` 命中面积极小（已隐藏永远是少数），索引只拖慢每轮写入
  （与 0020 的 `hidden`、0021 的 `hot_score_at` 同一判断）。
- **审计**：新增 `comment.hide` / `comment.restore` 两动作，detail 带
  `{ reason?, content（前 50 字）, newsTitle, userName }`——评论没有标题，
  审计时间线只能认内容片段（运营认内容不认 id）。
