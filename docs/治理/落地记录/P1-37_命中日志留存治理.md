## 批次 P1-37（2026-10-17）：命中日志留存治理（C7）
backlog 规则生效后的第五批：偿还最上方的 C7（合规项）。

**问题**：`sensitive_hits` / `nickname_hits` 的 `snippet` 存的是**用户原文**
（脱敏不可逆，它是误杀复盘与申诉的唯一证据），但**没有任何保留期限**——
日志只增不减，用户原话被无限期保存。这是数据最小化原则下的合规风险，
且旧日志本身也几乎没有证据价值（申诉都发生在近期）。

**方案：保留期 + 无保底 + 双触发清理 + 可见范围确认**

| 项 | 取值 / 做法 |
| --- | --- |
| 保留期 | `HIT_LOG_KEEP_DAYS`，默认 **90 天**；`0` = 不清理（仅取证期临时使用） |
| 保底条数 | **无**。与 `prune_old_news` 的 `keep_min` 刻意不同：保留期就是它的全部价值，保底会留下一批最旧的用户原话，反而违背「最小留存」 |
| 清理时机 | ① **每次启动扫一遍**（`lifespan`，不依赖任何 cron——`FEED_CRON_ENABLED=false` 时抓取 cron 不跑，合规清理不能跟着停）；② 抓取 cron 每轮顺带清理（与搜索日志/健康事件同一处） |
| 实现 | `app/hit_logs.py::prune_hit_logs()`：按 `created_at < now - keep_days` 删两张表，返回各表条数；A3 之后时间列同为 UTC aware，字典序即时间序 |
| 可见范围 | 仅 `GET /api/admin/moderation/hits`、`GET /api/admin/nickname-hits`，二者受 **C6 的 router 级管理员鉴权**保护；公开接口不返回 `snippet`（全仓 grep 确认无公开出口） |

**两个刻意的取舍**

1. **启动时清理**：合规要求是"过期即删"，不能因为运维把抓取 cron 关掉就停止删除。
   启动清理失败只告警、不阻断启动——合规尽力而为，但不该让服务起不来。
2. **累计计数不回退**：`nickname_words.hit_count` 是聚合值，删日志不影响它。
   "这个词历史命中过多少次"（发现高频词/误杀大户）与"还能看到多少条原文证据"
   （申诉材料）是两个问题，混在一起会让两个指标都失真。
