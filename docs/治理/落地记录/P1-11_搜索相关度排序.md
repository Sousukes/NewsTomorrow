## 批次 P1-11（2026-10-14）：搜索相关度排序（路线图 §2 第 2 项的剩余部分）
- **问题**：搜索是 `ILIKE` 召回 + **纯时间倒序**——搜「暴雨」时，标题含「暴雨」的旧文
  可能排在一堆只是发得新的弱相关文章后面。P1-8 做热词统计时把「全文相关度排序」
  挂起，条件是"需在真实 PG 上验证排序质量后再上"；P1-10 已验证本地 PG 可用，
  前置条件满足，本轮落地。
- **排序信号分三层**（`app/routers/news.py::_search_ranked`）：
  `100×标题整词命中 + 10×摘要整词命中 + 2×similarity(标题) + similarity(摘要)`，
  再按时间、id 倒序兜底。加分远大于相似度最大贡献（3），**层级严格成立**；
  相似度只在层内细排（标题更短、关键词占比更高的排前）。
  SQLite / 无 pg_trgm 环境退化为「标题命中优先 + 时间倒序」，语义同构。
- **两个关键设计决策（都有实测依据，不是拍脑袋）**：
  1. **不用 `tsvector` + `ts_rank`**（路线图原方案）：PG 内置分词器**不做中文分词**，
     连续汉字整体一个 token，`to_tsquery('simple', '暴雨')` 匹配不到「暴雨蓝色预警」；
     zhparser 需编译扩展，超出部署能力。pg_trgm 按字符三元组算相似度，对中文天然有效。
  2. **召回用 ILIKE 而非 pg_trgm 的 `%` 运算符**：`%` 默认阈值 0.3 对中文短词几乎召不回，
     调低阈值又因**大小写敏感**（`AI` vs `ai`）与**长词稀释**造成召回缺口
     （实测 `AI` 少 2 条、单字「暴」少 2 条）。而 **ILIKE 可直接吃 0005 的 GIN 索引**
     （EXPLAIN 实测 `Bitmap Index Scan on ix_news_title_trgm`），大小写不敏感、
     无阈值、与旧行为召回口径完全一致；短词才退化为全表扫描（毫秒级、结果正确）。
- **真实 PG 验证**（backlog 挂起项的验收条件，`scripts/verify_search_ranking.py`）：
  - 召回口径与 ILIKE **逐词一致**（暴雨 1 / 新能源 2 / AI 39 / 芯片 2 / 暴 3）；
  - 分层不变式成立：标题命中全部先于摘要命中（如「芯片」：标题命中的 Maia 300
    排在摘要命中的华为文前面）；
  - 「暴雨」「暴」的正确文章从旧排序的末位升到首位；「新能源」下更聚焦的
    《新能源汽车出口连续三月创新高》压过旧排序首位的长标题政策文；
  - 大小写不敏感（q=ai 与 q=AI 均召回 39 条）；多字关键词走 GIN 索引，无全表扫描。
- **顺带修复**：ILIKE 模式串未转义——用户输入 `%` 会被当通配符，"搜一个字符
  匹配全部"（既是错误结果也是信息收集面）。统一 `_escape_like()` + `ESCAPE '\'`。
- **测试**：后端 233 → **237 项**（`test_api.py` 新增 `TestSearchRanking` 4 项：
  标题命中高于摘要命中、同层级时间新的在前、`%`/`_`/`\` 通配符转义后只按字面匹配、
  排序与 offset 分页叠加、响应契约形状不变）。前端无改动（契约未变）。
  契约检查 mock 与真实后端各一遍均 **37/37**（真实后端这次端到端走过 PG 新排序路径）。
- **迁移**：**无**（复用 0005 的 pg_trgm GIN 索引），`alembic check` 无漂移。
- **踩坑**：
  - **PG 内置 FTS 对中文不可用**是"知识坑"而非"调试坑"——读文档时以为
    `tsvector` 是银弹，实测前先想清楚分词器对 CJK 的行为；
  - **pg_trgm 的 `%` 运算符与 GIN 索引服务的是两个东西**：`%` 受 GUC 阈值支配，
    而 ILIKE 能直接吃同一个 GIN 索引且无阈值问题——选召回方式前先用 EXPLAIN 验证；
  - 测试 URL 里的 `%`/`_` 必须显式 `quote()`，否则测了也白测（编码歧义）。
