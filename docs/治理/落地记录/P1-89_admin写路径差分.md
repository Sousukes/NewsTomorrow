## 批次 P1-89：admin 写路径差分 + 错误码取值比对

## 背景

P1-88 做了写路径回放，但只覆盖 `/me/*` 与 `/news/*` 的 4 条。
admin 写端点（下架 / 恢复 / 处置）是**运营实际操作的功能**，
一旦两端漂移，直接影响"演示正常、生产排障对不上"——是本批的扩展目标。

## 一、新增 4 条 admin 写用例

| 用例 | 撤销方式 |
| --- | --- |
| `POST /admin/news/n1/hide` | **成对**：紧接 `restore`，净状态为零（`hiddenAt`/`hiddenReason` 都被清）。各留一条审计记录，与 `contract-check.mjs` 既有做法同口径 |
| `POST /admin/news/__no_such__/hide` | 无（错误路径，不改状态） |
| `POST /admin/comments/__no_such__/hide` | 无 |
| `POST /admin/reports/99999999/resolve` | 无 |

后三条是**错误路径**：不需要合法 id，零状态变更，专比信封与错误码。
`needs: 'admin'` 字段让它们在账号不是管理员时明确 SKIP，而不是假装通过。

首轮 **8 条写用例全过、撤销零失败**，总 **35 passed / 0 failed**。

## 二、顺带补上「业务 code 取值比对」

原差分只比**形状**：`code` 两边都是 `number` 就判通过。
于是"真后端 40405 / mock 40404"这种漂移**永远抓不到**——而前端是按 `code`
分流的（`api/http.ts` 的 `code` 决定走哪个错误分支），code 不同就是契约不同。

加上取值比对后，27 条 GET 用例仍然全过（说明 GET 路径的 code 没有漂移），
说明这条比对不是无的放矢。

**反向变异验证**：把 mock 的评论隐藏 404 从 `40405` 改成 `40404`，
差分精确报出 `业务 code 40404 ≠ 40405` —— 这正是形状比对结构上看不见的那类差异。

## 三、刻意不做

- **admin 评论的 hide/restore 真写**：需要"先建评论 → 拿各自 id → hide → restore → delete"
  五步链，而 mock 与真后端的评论 id 规则不同、`findComment` 的查找范围也不同。
  链越长，中途失败留脏数据的概率越高；收益（多覆盖一个端点）不抵风险。
  已用错误路径覆盖它的信封与错误码。
- **`PATCH /admin/news/{id}`（置顶）**：撤销需要先读当前 `isTop` 再改回，
  三步链且依赖读到的状态；置顶是低频操作，留给你情急时手动验。
- **`/admin/words`、`/admin/sources` 的增删**：会在开发库留下真实的词条/源配置，
  而这两个是**全局生效**的运营数据，不像 hide/restore 有天然的对偶撤销。
