## 批次 P1-55（2026-10-18）：D1 最终定案——「只排序/只写入」列不迁

按上一批的约定，下一步是迁剩余「只排序/只写入」列、收尾 D1-1。动手前逐列
核实了 SQL 用法与写入路径，结论是**这些列不该迁**，D1 到此定案。

## 逐列核实（这是本批的全部产出——不是代码，是证据）

| 列 | 实际用法 | 结论 |
| --- | --- | --- |
| `user_history.viewed_at` / `user_favorites.created_at` | 排序键，但写入走 `_merge`（`func.max` + `_parse_iso` + `.isoformat()` 时间算术） | 迁类型要连带改 `_merge_base` 参数类型 |
| `comment_likes.created_at` / `message_reads.created_at` | 只写入 | 纯写入，收益仅类型诚实 |
| `comments.hidden_at/deleted_at/reviewed_at`、`news.hidden_at`、`users.name_reviewed_at` | 只写入，**但有输出点**（`hiddenAt`/`reviewedAt`） | 逐个过 `iso_utc` |
| `rss_sources.last_fetched_at/next_retry_at` | `alert.py` Python 侧 `_parse` 比较 + 输出点 | 同上 |
| `search_logs.created_at` | `>= cutoff`/`< cutoff` 范围过滤 | 属 D1-2 |
| `messages.created_at` | `coalesce(created_at,'')` 排序键 | 换 `NULLS LAST` |

**关键发现：根本没有「纯」的低价值列。** 连「只写入」都只是表象——要么写入
路径纠缠着 `_merge` 的时间算术，要么有输出点要逐个改。为「类型诚实」付出
这些验证面不划算：P1-53 已经用一次静默毁数据证明，这类迁移的真实风险
远超纸面收益。

## D1 最终范围

1. **已迁**：`rss_source_health_events.at`（0030）——D1 里唯一「现在就有功能
   价值」的列（窗口查询用上真实类型 + 参数绑定）；

   把保留期清理下推数据库、或做时间窗口聚合时再迁，工具与演练已就位。

## 为什么「不迁」也是个值得记录的交付

一连串批次（P1-51 证伪 D1-a → P1-53 首列 + 翻车 → P1-54 工具化）最终收敛到
「只迁了有真实价值的那一列」。这不是半途而废，而是**用证据收敛范围**：
每一步都把「还剩什么、值不值得」问一遍，答案是"不值得"就停下来写清楚。
比"为了收尾而把 10 个低价值列都迁一遍"诚实得多。
