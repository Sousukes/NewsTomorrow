## 批次 P1-34（2026-10-17）：前端列表状态分桶 + 竞态守卫（A4）
backlog 规则生效后的第二批：偿还最上方的 A4（P0 组最后一项）。

**问题**：`stores/news.ts` 只有一个 `list` + `currentChannel` + `currentSort`，
首页与视频页共用同一份列表状态。两个具体后果：

1. **串页**：视频页 `fetchNews('video')` 直接覆盖 `list` 并把 `currentChannel` 改成
   `video`；首页被 KeepAlive 缓存，切回时渲染的是视频内容，且触底 `loadMore()`
   会按 `video` 频道继续往首页列表追加。
2. **竞态**：`fetchNews` / `loadMore` 之间没有任何代次或取消机制。`loadMore` 在途时
   用户切频道，旧响应到达后执行 `list = [...list, ...fresh]` 并覆盖 `cursor`——
   旧频道条目混入新列表、后续翻页按错误游标续接。

**方案：按 (频道 × 排序) 分桶 + 代次守卫**

- `NewsBucket`：每个组合一份独立状态（`list/loading/error/page/total/hasMore/
  loadingMore/cursor/generation`）。桶在 store 初始化时**预建**全部组合
  （7 频道 × 3 排序 = 21 个），避免渲染期按需创建触发额外更新。
- **按排序也分桶**（而非仅按频道）：排序键变了服务端游标即失效，同频道不同排序
  本就是两份不同列表；顺带获得「切回原频道/原排序时列表还在」的体验。
- **代次守卫**：`generation` 每次 `fetchNews` / `resetPaging` 递增；`loadMore` 捕获
  调用时的代次，响应回来若代次已变则**整体丢弃**——不追加、不覆盖 `cursor`、
  不改 `hasMore`，也不误清 `loadingMore`（由新请求接管）。同一桶内「先发的 fetch
  后返回」同样被丢弃。
- **API 显式化**：移除全局 `list/currentChannel/currentSort/page/total/hasMore/
  loading/loadingMore/cursor/error`，改为 `bucketOf(channel, sort)` /
  `listOf(channel, sort)`；`fetchNews` / `loadMore` / `resetPaging` **必须显式传**
  频道与排序。不再有「隐式当前频道」——这是根因，留着它就会复发。TypeScript 会把
  全部调用点暴露出来（本次只有 `stores.spec.ts` 需同步，说明改动是收敛的）。
- `getById` 改为遍历全部桶 + 详情缓存 + mock，收藏/历史页渲染不受分桶影响。
- `loadDetail` 不再借用列表的 `loading`/`error`：此前打开详情会让首页出现骨架，
  且详情失败会污染列表的错误提示。

**视图层**

- `HomeFeed`：`bucket = computed(() => news.bucketOf(activeChannel, activeSort))`，
  模板与 `useInfiniteList` 全部读 `bucket.*`。
- `Videos`：固定 `video` 桶，与首页完全隔离；顺带补上**无限滚动 + 骨架 +
  空/错误/末页提示**（此前只显示第一页 20 条，且无任何状态反馈）。

**测试**：前端 484 → **488 项**（`stores.spec.ts` 净增 4 项：新增「分桶隔离」3 项 +
「竞态守卫」4 项，同时把原有 11 项列表/排序用例改写为桶 API）。新增用例：

- 不同频道的列表互不覆盖（首页与视频页不再串页）
- 同一频道不同排序各自成桶
- `getById` 可命中任意桶
- **`loadMore` 在途时重新 fetch，旧响应被丢弃（不追加、不覆盖游标、不卡住 `loadingMore`）**
- **先发的 fetch 后返回时不覆盖后发的结果**
- `resetPaging` 使在途 `loadMore` 失效
- `loadMore` 续接沿用桶的排序

**无后端 / 契约 / 迁移变更**（纯前端）。`npm run verify`（类型 + Lint + 格式）与
`npm run build` 均通过。
