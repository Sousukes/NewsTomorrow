## 一、把重建逻辑抽成公共工具

`app/migration_utils.py::convert_column_type()`：反射 → 建新表 → **Python 逐行转换**
→ 换名 → 按**反射到的真名与真列**重建索引。

关键设计：**索引不用人记**。P1-53 我自造了一个名字相近但语义不同的索引，
把「复合索引没了」掩盖成「名字不对」；现在索引直接来自 `get_indexes()`，
下一个人不可能再搬错。

配套 `tests/test_migration_rebuild.py`（**13 项**）覆盖通用场景：
多列/多索引/外键/`ondelete`/NULL/脏值/临时表清理/列类型真的变了，
以及一条**行为**断言——删父行子行确实被级联清掉（不只是元数据对）。

## 二、工具自己暴露的两个问题

1. **计数恒为 0**：先把原值覆盖成 `parsed`，再判断「原值是否非空」→
   脏数据被静默写 NULL，而日志说"没有脏数据"。**先取原值再覆盖**。
2. **NOT NULL 列遇到脏值 = 崩溃**：写 NULL 会撞约束，错误信息只有
   "NOT NULL constraint failed"，看不出根因是"值不是时间"，而且临时表已经建了。
   改成**两段式**：先扫描收集脏行，确认能过再开始建表；过不了就抛带样本的
   `RuntimeError`，**数据库一个字节都不动**。这与 0027/0029「不编造」的立场一致：
   宁可停下来让人处理，也不要迁移出一张被静默改写过的表。

## 三、CI 多了一步「带存量数据的 PG 演练」

原先 CI 的 `alembic upgrade head` 跑在**空库**上——只验证了 PG 分支的**语法**，
没验证**存量转换行为**，而后者才是出问题最贵的地方。

新增（`scripts/_migration_drill.py` + 一段 CI 步骤）：
造几条真实格式的存量行 → 迁到 head → 断言**值完整、瞬时正确、偏移未被改写、排序正确**。
PG 与本地 SQLite 共用同一个脚本。

演练脚本自己也暴露了一个真问题：种子里的 `NULL` 行**插不进去**——
`rss_source_health_events.at` 是 NOT NULL。写出来才发现，而那正是这个脚本
要避免的事。**NULL 场景改由 helper 单测覆盖**（helper 遇到它会明确失败）。

另有一处断言写得太严：直接要求文本含 `+00:00`，在 SQLite 上必然误报——
**存储形态**（SQLite 不带偏移）与**对外格式**（`iso_utc` 负责补）是两件事。
已改为断言**瞬时**（两端通吃的唯一不变量）。
