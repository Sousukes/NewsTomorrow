## 批次 P1-29（2026-10-18）：消息列表按真实时间排序（A2）
消息列表此前按 `Message.id DESC` 排序、游标用 `Message.id < cursor`，而互动
消息的 id 是 `msg_{uuid4hex}`——**随机串**。排序与真实时间无关（最旧的消息
可能排在最前，与 `time` 文案脱节），keyset 游标语义失效（「末条之后」翻出
来的可能比它更晚，翻页会重复或遗漏）。

- **迁移 0026**：`messages.created_at`（String(30)，**可空、不设 server_default**）。
  存量行没有可信时间源——`time` 列存的是「1小时前」这类相对文案，不能反推
  绝对时间，**回填等于编造数据**；新消息由模型 `default=now_str` 自动写入，
  `notify.py` / `alert.py` / 种子无需逐个改动。
- **排序键 `coalesce(created_at, '')`**：与 `news.published_at` 的 `_PUB`
  同款处方——空串在 DESC 下排最后，存量行自然沉底，且 PG 与 SQLite 行为一致
  （不依赖 `NULLS LAST`，两者语法支持度不同）。同秒用 `id DESC` 决胜，
  保证分页稳定。
- **索引 `ix_messages_created_at` 是单列**：可见范围是
  `user_id = X OR user_id IS NULL`（OR），`(user_id, created_at)` 复合索引
  走不了；单列索引服务 ORDER BY，避免每页全表排序。
- **游标格式不变**（仍是上一页末条的 id）：服务端按该 id 回查排序键
  （锚点查询同样带 `visible_condition`），取「严格更早」的一页。不把时间戳
  编进游标的理由：老格式游标继续可用、前端零改动、键值以库中权威行为准
  （客户端改游标也翻不出可见范围）。锚点不可见/已删 → 忽略游标回第一页
  （消息没有清理任务，这只在手工删数据后出现，「从头开始」比报错更不影响使用）。
- **种子**：`MESSAGES` 补 `_offset_min`，`init_db` 写 `created_at=_ago(offset)`
  （m1 刚刚/m2 1小时前/m3 2小时前/m4 1天前，与 time 文案一致）。
- **踩坑（ORM 显式 None ≠ 数据库 NULL）**：测试想造「存量 NULL 行」时用
  `Message(created_at=None)` 构造，**模型 `default=now_str` 在值为 None 时
  照样触发**——插进去的是「现在」的时间戳，排序断言全反（NULL 行排到了最前）。
  真正的存量行只能用 raw SQL 插。第一版测试就是这么错的，两个失败断言
  （NULL 沉底 / 翻页首页）把我引到了根因。
- **回归**：后端 pytest 611 → **618 全绿**（`TestMessageOrdering` 6 项：
  时间倒序 / 存量 NULL 沉底 / 同秒 id 决胜 / 翻遍全表不重不漏且收敛 /
  他人消息 id 当游标回第一页 / 模型默认值自动写入；`test_migrations.py` +1
  0026 列与索引断言）。**前端无改动**（游标对前端是不透明的，排序在服务端）；
  mock 服务没有 messages 路由，契约检查不涉及本端点（维持现状）。
