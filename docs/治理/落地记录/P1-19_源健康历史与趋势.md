## 批次 P1-19（2026-10-15）：源健康历史与趋势（当前健康字段只是一个点）
- **背景**：P1-16~P1-18 把「当前状态」做到了位，但那始终只是**一个点**——`last_status`
  只有"现在挂没挂"，`last_item_count` 只有"最近一次抓到几条"，`consecutive_failures`
  只有"连着挂了几次"。没有时间维度，四个问题一个都答不了：

  | 问题 | 为什么当前字段答不了 |
  | --- | --- |
  | 它今天才开始烂的，还是已经烂了两周？ | 没有历史，只有最后一次的结果 |
  | 是不是每天凌晨固定抖？ | 单点看不出规律，只会以为是随机抖动 |
  | 上次改了地址/权重，有好转吗？ | 改动前的基线没有留存 |
  | **一直返回成功，但条数从 30 掉到 3 条？** | **它永远是绿的——结构性看不见** |

  最后一条是本批真正的靶子：**"成功但条数持续下滑"的源，用现有任何字段都发现不了**。
  本批刻意排在 P1-18 之后——等 `failure_kind` 等字段稳定了再往上盖时间维度。
- **设计①：存原始事件，不存每日聚合**（`rss_source_health_events`，每轮一行）。
  理由与 `SearchLog` 同源：聚合表只能表达"历史累计"，事后想换个窗口（7 天 / 30 天）
  重看就没数据了。代价是需要清理，见 ③。
- **设计②：只记真实尝试**。按礼仪或熔断跳过的源本轮根本没发请求，给它记一行会
  伪造出"尝试过"的痕迹——与「跳过的源不刷新健康状态」是**同一条口径**
  （`run_ingest` 的 `finally` 里与 `record_fetch_result` 相邻，两处各自提交、各自吞异常）。
  因此趋势图上的空白 = 那时没抓它，**不是失败**；前端据此铺格子，缺的天不补零
  （补零会把"没抓"伪装成"抓了但全失败"）。
- **设计③：按时间清理，不设条数保底**（`FEED_HEALTH_KEEP_DAYS`，默认 30 天）。
  与 `prune_old_news` 的 `keep_min` 刻意不同：健康历史是排障取证用的，
  保底条数只会留下一堆最旧的噪音，而"最近 N 天"就是它的全部价值。
  同样刻意不建 `at` 单列索引——清理查询在两万行量级上全表扫描只要几毫秒，
  不值得为此拖慢每轮十几次写入；只建复合索引 `(source_key, at)`。
- **设计④：`avgItems` 取成功轮次的平均**，不是全部轮次：失败轮天然 0 条，
  混进来会让"条数退化"被失败率掩盖——而这正是本批要抓的第二类隐形故障。
  `rate` 在无尝试时返回 **None 而不是 0**：`0` 会把"没抓过"伪装成"全挂了"，
  运营会去排查一个根本没跑过的源。
- **设计⑤：列表只放摘要，趋势放单源**。`GET /api/admin/sources` 每行附 `health`
  （`attempts` / `rate` / `avgItems`，一条 GROUP BY 查全部源，避免 N+1）与 `healthDays`；
  列表回答"哪个源值得点进去"，`GET /api/admin/sources/{key}/health` 才回答
  "**它到底怎么了**"——三段数据各有分工：

  ```
  summary  窗口总览（成功率 / 成功轮均条数）  → 是抖动，还是持续恶化？
  points   按天序列                            → 是不是每天固定挂（对方维护窗口）
  failures 最近失败原文 + kind                 → 要不要去改 URL / 换源
  ```

  `days` 由 `window_days()` 收敛到保留期：请求 90 天而只留 30 天，只会得到 60 个空格子。
  响应回传实际生效的 `days` 与 `keepDays`，前端才能正确标注时间范围、
  并向运营解释"为什么最多只能看这么久"。
- **前端表达**：源列表每行一个健康 chip（`<0.5` 红 / `<0.9` 琥珀 / 无尝试灰色"—"），
  点「趋势」就地展开 `SourceHealthTrend`（一次只开一个，失败只在行内报错不掀页）。
  趋势面板有四指标 + **两条只有历史看得见的结论**，都是把输出打出来读过才定的阈值：
  - **条数下滑**：成功轮均条数前后半对比，"最近不足前期六成"且样本 ≥4 天才提示；
  - **规律抖动**：≥3 次失败且六成以上落在同一小时 → "像是对方站点的维护窗口"。
  格子按 `days` 铺满再按日期落点，**无数据日留浅底空格**（不伪装失败）；
  全失败日柱子高度强制 `6%`，避免 0 条塌成零像素看不见。
- **两类隐形故障各有自证用例**（本批测试的核心价值）：
  `test_success_with_declining_items_is_visible`——5 轮全成功、条数 30/24/18/9/3，
  断言 `rate == 1.0`（老口径满分）而 `items` 单调下滑；
  `test_periodic_downtime_shows_up_as_a_pattern`——每天 1 成 1 败，
  断言失败全部落在同一钟点（单看任何一轮都只是随机抖动）。
- **踩坑（mock 种子从未生效）**：P1-18 埋的 `SEEDED_FAILURES` 用了两个**不在
  `BUILTIN_SOURCES`** 里的 key，种子从没生效过，而用固定 fixture 的单测照样全绿
  ——mock 下永远看不到失败分级 UI 分支。本批改为真实内置源 key 并加注释。
  **教训：mock 种子的 key 必须存在于内置源清单，否则是一类静默失效。**
- **踩坑（测试时间戳跨午夜）**：初版用"相对现在往前推 N 小时"构造"同一天两条"，
  在 00:xx 跑会把事件甩到相邻日期，按天分桶的断言凌晨随机失败。
  改用**整点锚点** `BASE`（5 天前的 00:00）往后推。
