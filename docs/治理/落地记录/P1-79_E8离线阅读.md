## 五个实现要点

1. **副本是"刚看的 + 收藏的"，不是本地档案馆**：条数上限 30、保留期 7 天。
   localStorage 只有 5 MB，副本无限增长会挤掉 marks/exposures——而那两份是
   功能数据（收藏拿不回云端）。
2. **超限条目整条不落，不落半个**：后端单条正文可达 8000 字（E1），
   一条异常长文就能吃光配额；落半个资讯比没有更糟。
3. **`fromCache` 标记必须传到 UI**：静默展示旧内容等于骗人，用户至少该知道
   "这是断网前存的"。详情页与壳层横幅各一处提示。
4. **回落分支要按冷启动测**：同一会话内 `detailCache` 会先命中，走不到回落；
   真实场景是"断网重启后内存已空"。测试里用**重建 pinia** 模拟。
5. **图片缓存必须放行图片代理所在源**：`proxiedImageUrl()` 产出
   `${API_BASE}/api/img?…`，而 `VITE_API_BASE` 完全可以是另一个源（静态站 +
   独立 API 域名是最常见部署）。只认同源会让这类部署下一张配图都缓存不到。

## 与设计的偏差（有依据）

- **写操作的本地暂存没有新做**：核实代码发现 `toggleFavorite` 早就是
  "本地先落盘 → 再推服务端"（`persistMarks()` 在 `pushFavorite()` 之前），
  失败留 `syncError`、下次登录/启动时 `syncMarks` 并集合并——D6 要的
  "仅 marks 值得本地暂存"**已经是现状**，再包一层只是重复。
- 评论/举报等写操作维持"明确失败"：没有幂等键在本地，排队重发会重复计数。
