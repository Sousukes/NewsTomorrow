## 批次 P1-50（2026-10-18）：D1 决策准备 + 修掉时间展示的真 bug

按上一批的判断执行：**D1（`String(30)` → `TIMESTAMP`）不该由 backlog 顺序
决定何时做**。它是 L 级、一次性迁移，且与已完成的 A3 时间口径改造直接相关。
本批**不改 schema**，只做两件事：把改之前必须知道的事查清楚 + 把安全网钉住。

## 盘点结论

36 个 `String(30)` 列分三类：绝对时间戳（A3 后统一 `now_str`）、**展示文案**
（`news/comments/messages.time`，根本不是时间）、业务 ID。所有 `String(30)`
的 `default=` 全是 `now_str`，没有漏网的 `DateTime`——这部分比预想干净。

真正的风险面在**比较发生在哪里**：
- **SQL 侧字符串比较**：`feeds/health.py` 的 `at >= cutoff`（cutoff 是 ISO 串）；
- **Python 侧比较**：`feeds/alert.py` 的 `_parse(...)` 与 aware datetime 比。

同一列在两端被比较的方式不同，改列类型时行为变化也不同——这才是 D1 的成本所在。
完整清单见 [`docs/后端/时间字段盘点与D1决策.md`](../../后端/时间字段盘点与D1决策.md)。

## 顺手修掉的真 bug（用户可见）

`comments.time` / `messages.time` 同时装着两种东西：用户新建路径写的是
**ISO 串**（`time=ts, created_at=ts`），演示种子写的是**「1小时前」**，
而 `to_out` 原样透传 —— 于是**用户刚发的评论显示 `2026-10-18T14:42:17+00:00`**。

修法不是「换一种存法」（那要迁数据），而是**展示文案由绝对时间推导**：
新增 `models.display_time(stored, absolute)`，输出侧统一调用。能解析成 ISO 的
现算相对文案；已经是展示文案的**原样保留**（那不是时间，是排版效果）；
都没有就回落到另一列。

这同时消掉了 D1 的一个障碍：展示型列不再需要两种格式共存，改类型时可以直接
把它们排除在迁移范围外。

## D1 的安全网

`tests/test_time_contract.py`（**14 项**）把「同格式 ISO 的字典序 = 时间序」
这条契约钉住——A3 统一了写入口径、0027 回填了存量偏移，**但此前没有任何断言
守着它**。契约一破，排序会静默出错，而症状是「列表顺序有点怪」，极难定位。

其中 naive 检查**用 AST 扫调用节点而非子串匹配**：文档字符串里那句
「不要再引入 `datetime.now()`」会把护栏自己绊倒——**护栏被文档绊倒一次，
就再也不会有人看它了**。

## D1 建议分两批（写进决策文档的结论）

- **D1-a（低风险）**：只排序、不参与 SQL 范围过滤的列；
- **D1-b（需设计）**：参与 SQL 范围过滤的列（cutoff 改参数绑定）。

另有两处必须同步处理：① `coalesce(x, '')` 改类型后会**类型错**，要换
`NULLS LAST`；② SQLite 无原生时间类型，迁移脚本必须**分方言**、downgrade 空操作。
